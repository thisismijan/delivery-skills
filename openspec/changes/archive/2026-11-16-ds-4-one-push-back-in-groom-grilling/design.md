## Context

`/groom` grounds itself with a read-only `groom-explorer` (step 3), then grills the operator one question at a time (step 5) and appends each settled choice to `decisions.md` in the grooming output directory. Nothing compares a pick with what the explorer found, and the explorer's report is held only in the conversation. A pick that contradicts the codebase therefore goes into the ticket unchallenged and surfaces later in `/draft` or `/execute`. This design adds one evidence-based challenge, puts the report where it can be cited, and gives the challenge a record a script can check.

The record has to fit how `decisions.md` is really written. Real logs (for example the one for the elephant-goldfish grooming run) have these traits: ordinary entries are consecutive lines with no blank line inside (`Question:`, `Options:`, `Pick:`, `Withheld recommendation:`, `Differed:`), `Agent decided:` lines and the next `## ` heading follow straight after an entry, a later session is appended under a new `## ` heading (an `## Addendum`), and every ordinary entry already carries a `Question:` line. The same title always derives the same output directory, so a re-run lands in the same files.

## Goals / Non-Goals

- Goals: one challenge per contradicting pick, quoting the explorer's evidence; the operator's final decision is recorded with the challenge and never overridden; no challenge without a quotable passage; a challenge record that a script can refuse when it is malformed, decorated, or cites nothing real, without tripping over the rest of a real log
- Non-Goals: push-back in `/draft` or any other stage; challenging on grounds other than the explorer's report; blocking the operator; deciding by script whether a pick contradicts the evidence; changing `factory/agents/groom-explorer.md`

## Decisions

- **Where the evidence lives:** groom appends the explorer's report word for word to `explorer-report.md` (new file name) in the grooming output directory, in step 3, before the first question. Each session adds one section under `## Session <ordinal>`; the ordinal is one more than the `## Session` headings already in the file, or one for a new file. Earlier sections are never overwritten, so a quote from an earlier session stays checkable after a re-run. The explorer has only Read, Grep, and Glob, so it cannot write the file, and its report format is unchanged. The file sits beside `decisions.md` as a run log, and every write goes through `groom-paths.ts verify`. When the explorer is skipped (step 2a), no section is appended and nothing is challenged in that session. Both step 2a shortcuts, the plain zero-exit one and the one that fills the housekeeping sections, record their `Agent decided:` line in `decisions.md`, so the decision log exists for the step 8 check, which fails on a missing log.
- **What counts as a contradiction:** a passage in the report that disagrees with the pick, for example the report lists a module, seam, or domain term that the pick says does not exist or says to replace. That is a model judgement and stays in the skill. The one hard rule is that groom must be able to quote the passage. No quotable passage means no challenge, which is how a supported pick, or a pick the report is silent on, goes through untouched.
- **When the challenge is raised:** on the pick the operator has settled. For an operator-owned question that is after the withheld recommendation is revealed and any change the operator makes then, so a pick changed at the reveal is checked as the settled pick and the challenge never races the reveal. Groom spends one turn on the challenge: quote the passage, name the pick, ask keep or change. It is that turn's single question, so the one-question-per-turn rule holds. The challenge is raised before that question's entry is appended, so the entry and the five challenge lines are written together once the operator decides. The settled pick is the pick standing after the recommendation reveal and any change, so `Challenged pick:` is the settled pick being challenged, never the pick as first given before a reveal-time change. It does not use the multi-option Human decision brief, because there are only two answers and the operator's own pick is not hidden. The `Final pick:` in the entry is the pick recorded after the challenge.
- **What follows:** whatever the operator answers is recorded and groom moves on. It does not ask about that pick again, does not challenge a changed pick, and does not block or override the final pick.
- **How the challenge is recorded:** exactly five consecutive lines, appended directly after the `Differed:` line of the question's ordinary entry:

  ```
  Challenged pick: <the settled pick being challenged>
  Challenge question: <the question that was asked>
  Evidence: "<passage quoted from explorer-report.md>"
  Operator decision: kept | changed
  Final pick: <the pick recorded after the challenge>
  ```

  The entry ends after the `Final pick:` line. A blank line, an `Agent decided:` line, or the next heading that follows is simply not part of it and is never an error, so the check does not depend on blank lines that real logs do not have. `Challenge question:` is a new label, distinct from the ordinary `Question:` lines, which the parser never reads. `kept` means `Final pick` equals `Challenged pick`; `changed` means it differs. The marker and labels are exported from `factory/scripts/groom-decisions.ts` (new), so the skill's wording is tested against the same names the script parses.
- **Evidence line:** the passage is the text between the first and the last double quote on the `Evidence:` line, so a passage that itself contains double quotes (a string literal from the code, say) parses. It must sit on one line; a wrapped continuation line fails the next-label check. Whitespace runs inside the passage and in the report are collapsed to one space before the search; case and wording must match.
- **Fail closed on decoration:** the parser never treats an unrecognised marker as no challenge. Any line whose plain text starts with `challenged pick` is refused unless it is the start of a well-formed entry. The plain text is the line with asterisks and backticks stripped, leading spaces, list markers, quote markers, and heading marks removed, and case ignored. This is the same stripping `plain` does in `factory/scripts/workflow-contracts.test.ts`, plus the leading markers a model puts in front of a label. So `**Challenged pick:**`, `- Challenged pick:`, `Challenged Pick:`, and an indented marker are all refused. Only an undecorated, case-exact marker line followed by the four exact label lines in order is an entry.
- **What a script checks:** `checkChallenges(decisionsText, reportText)` refuses a lookalike marker, a missing, empty, reordered, or duplicated line, an `Evidence:` value without a non-empty passage between two double quotes, an unknown `Operator decision:` value, a `kept` decision whose final pick differs, a `changed` decision whose final pick is the same, a passage not found anywhere in the report file, an empty or absent report, and a repeated `Challenge question:`. Its `check` mode prints JSON and exits 0, 1, or 2, as `verify-ticket.ts` and `groom-paths.ts` do. A missing `decisions.md` exits 1. A missing report file is read as empty, so a log with no challenges still passes when the explorer was skipped.
- **Repeat rule scope:** a repeat is the same `Challenge question:` text twice under the same `## ` heading of `decisions.md`. A later session appends under a new `## ` heading, so the same question under a different heading is not a repeat. That is cheap to check and cannot tell two sessions apart any better, so the rule is stated at that scope on purpose. Re-asking within one session stays a skill rule.
- **What only skill wording can pin:** whether a pick truly contradicts the report, that the challenge is a single turn, that a supported pick is not challenged, the order against the recommendation reveal, that groom never asks again or challenges a changed pick, and that the final pick is not overridden. The script cannot see the conversation. It does guard the evidence side: a challenge cannot be recorded without a passage that exists in the report, and a malformed or decorated record cannot slip through as "no challenge".
- **Where the check runs:** step 8 of the skill, before the `groom-writer` is dispatched or a valid source is copied, as `GROOM_DECISIONS_CHECK_INVOCATION`. A non-zero exit stops the run until groom corrects the current session's entries from the conversation. Earlier sessions' entries stay valid because the report is append-only. The check gates a bad record of the operator's pick, never the pick. The retro workflow later reads `decisions.md`, which makes a well-formed record worth enforcing.
- **Closed script list:** the Hard rules of `skills/groom/SKILL.md` say Bash is present only to run named local scripts. `groom-decisions.ts` is added to that list, so step 8's invocation does not break the rule the skill states.
- **No new verdict values, stop ids, or exit codes beyond the three the script states.** The constitution is unchanged. Human-facing problem messages are plain sentences.
- **Existing files touched:** `skills/groom/SKILL.md` (Hard rules and steps 2a, 3, 5, and 8) and `factory/scripts/workflow-contracts.test.ts` (new assertions in the "durable grooming" block).
- **New files:** `factory/scripts/groom-decisions.ts` (new) and `factory/scripts/groom-decisions.test.ts` (new). The scripts directory needs no registration for either.

## Test seam

- Primary: `factory/scripts/groom-decisions.test.ts` (new) calls `checkChallenges` with hand-written logs and reports. It includes a log shaped like the real `decisions.md` (ordinary `Question:` lines, an entry followed by an `Agent decided:` line, an entry followed by the next heading, no blank lines inside entries) and a report with two `## Session` sections whose earlier passage is quoted. It covers a passage with inner double quotes, a passage with repeated spaces, each malformed shape, each decorated marker, a passage absent from the report, an empty or absent report, a repeat inside one `## ` section, and the same question under two headings. It also runs the `check` mode as a subprocess for the exit codes 0, 1, and 2, including a missing `decisions.md` and a missing report file
- Contract: `factory/scripts/workflow-contracts.test.ts` asserts the groom skill, using the exported marker and label names rather than copies: step 3 appends under `## Session <ordinal>` after `groom-paths.ts verify` and never overwrites; a later session starts a new `## ` heading; steps 2a and 5 say a skipped explorer means no challenge; step 5 states the one-challenge, quote-the-passage, no-quote-no-challenge, after-the-recommendation-reveal, record-the-decision, never-ask-again, never-challenge-a-changed-pick, and never-override rules and names the marker, labels, `kept`, `changed`, and the placement after `Differed:`; the Hard rules list `groom-decisions.ts`; step 8 contains `GROOM_DECISIONS_CHECK_INVOCATION` before the writer dispatch and says a non-zero exit stops the run
- What it catches: a malformed, decorated, or fabricated challenge record, a quote that is not in the report, a repeated challenge in a section, a check that trips on real log shapes, a skill that drops a rule or names a different marker, a check that is missing or comes after the drafts, a script missing from the Bash list
- What it misses: whether a live groom run judges contradiction well, whether it really asks once and never again, whether it raises the challenge after the reveal, and whether a supported pick is left alone in a real conversation. Those are model behaviours. The boundary that needs a fake is the groom conversation itself: tests never run a live model or an operator, they read the skill wording and feed the script hand-written logs
- Held-out samples: none are needed, because no rule is written from sample data

## Risks / Trade-offs

- A model may challenge a pick that the report only loosely contradicts; mitigated by the rule that a challenge must quote a passage, and by the operator's decision being final after one challenge
- A model may skip the challenge when it should raise one; accepted, since the failure is the status quo, and the quoted-evidence record makes every challenge that did happen auditable
- The five-line shape is rigid, so a small slip in the log makes the step 8 check stop the run; accepted, because the stop names the line and the fix is a one-line edit to `decisions.md`
- A question challenged again under a new `## ` heading is not caught as a repeat; accepted, because sessions cannot be told apart more cheaply, and the skill rule still forbids asking again
- `explorer-report.md` grows by one section per session; accepted, because dropping old sections would make earlier quotes uncheckable

## Migration Plan

None. Behaviour starts on the next `/groom` after merge. Existing grooming folders have no `explorer-report.md` and no challenge entries, and a `decisions.md` without challenge entries passes the check.
