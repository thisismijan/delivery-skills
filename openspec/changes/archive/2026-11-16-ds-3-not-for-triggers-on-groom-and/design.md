## Context

`factory/scripts/skill-metadata.ts` (read by `factory/scripts/skill-metadata.test.ts`) walks every `SKILL.md` under `skills/` and reports frontmatter problems through `skillMetadataIssues(text, relativePath)`. Today it checks portable keys and the `$ARGUMENTS` placeholder, and it never reads a frontmatter value: `parseSkillFrontmatter` returns key names only. `skills/groom/SKILL.md` and `skills/draft/SKILL.md` describe only what they do. Both begin with a runtime-loading preamble and go straight to their steps, so a host that loads one for a passing question has nothing telling it to stop. This design adds trigger wording to the two descriptions, a first step in each skill, and a rule in the existing check.

## Goals / Non-Goals

- Goals: groom and draft descriptions name what starts them and what must not; loading a skill never authorises the run; one question settles an unnamed request before anything tracked is written; the metadata check enforces the not-for clause on covered skills with a rule a script can decide, and cannot silently lose coverage
- Non-Goals: clauses on other stage skills; changing groom or draft after a run is confirmed; more than one clarifying question; judging in a test whether a live model really stays quiet

## Decisions

- **Which skills the check covers.** The factory stage skills are `groom`, `draft`, `execute`, and `address-comments` (README, "portable factory stages"). `openspec-archive` is a bundled stage that is not part of the factory pipeline, and `delivery`, `code-review-max`, and `mr-review` are the conductor and the review pair. The ticket says to leave stage skills other than groom and draft alone, so a rule that failed every stage skill would turn the pack red on `execute` and `address-comments`. The check therefore covers a closed list, `NOT_FOR_STAGE_SKILLS` in `factory/scripts/skill-metadata.ts`, with the values `groom` and `draft`. A skill is covered when its parsed frontmatter `name` is in the list. Widening coverage later is one entry in that list plus the clause on that skill. No other skill is affected by the new rule.
- **Reading a frontmatter value.** `parseSkillName(text)` and `parseSkillDescription(text)` both return `string | null` through one shared reader, so the quote handling cannot differ. The reader takes the frontmatter block that `parseSkillFrontmatter` already delimits. The value is the text after the key on its line plus any following indented lines, joined by single spaces. A value that is only a block scalar marker (`>`, `>-`, `|`, or `|-`) takes its text from the indented lines under it. Surrounding whitespace is removed, then one pair of matching surrounding single or double quotes. It returns `null` when there is no frontmatter or no such key. Inline comments are not interpreted, so a name written with a trailing comment will not match any covered name, and the stale-entry rule below reports it.
- **What counts as a not-for clause.** The description contains a sentence that starts with the words `Not for` followed by a space and at least one more non-space character. A sentence starts at the beginning of the description or after a full stop, question mark, or exclamation mark and whitespace. The match is case sensitive. So `Not for a question about what a ticket means.` counts. These do not count: `not for ...` or `Do not use for ...` in lower case, `Not for` with nothing after it, and `Not for` in the middle of a sentence. The rule is `hasNotForClause(description: string): boolean`. There is no phrase list and no model judgement. A `null` or empty description for a covered skill has no clause, so it is reported.
- **The new issues.** `skillMetadataIssues` appends, for a covered skill whose description has no not-for clause, exactly `<relativePath>: stage skill '<name>' description has no not-for clause`. It names the skill both by path and by name. Existing issues are unchanged and still reported alongside it. `coveredSkillIssues(skillNames: string[]): string[]` returns `stage skill '<name>' in NOT_FOR_STAGE_SKILLS matches no skill in the pack` for each covered name that is not among the given names. This closes the hole where a renamed or mis-quoted skill, or a stale list entry, drops out of the check while the whole-pack test stays green. The whole-pack test passes it the parsed name of every real `SKILL.md`.
- **Start and not-for wording in the two descriptions.** Each description keeps what the skill does, then adds a sentence starting `Use when` that says what starts it, and a sentence starting `Not for` that says what must not start it. Each `Not for` sentence contains the words `a question about what a ticket means`. Descriptions use no colon followed by a space inside the value, because the value is a plain YAML scalar, and use no em or en dashes in the new sentences. The check itself requires only the not-for clause. The `Use when` sentence and the example words are pinned by the contract test in `factory/scripts/workflow-contracts.test.ts`, so the skill metadata check stays one rule.
- **Step 0, confirm this is a run, and when it applies.** Both skills get a step 0 placed before every step that fetches, derives a path, writes, or dispatches a worker. The step says, in these words: `Loading this skill does not authorise a run.` Step 0 applies only when the skill was loaded without being named. These are named invocations and never get the extra question: the operator typing the slash command (`/groom` or `/draft`) with or without an argument; the delivery conductor dispatching the stage, because the dispatch names the stage command; and any run that already has a run contract file `.delivery/runs/<id>.run-contract.json`, which is the same file draft's preamble already checks. A named invocation continues at step 1. Groom's step 1 keeps its own question when there is no usable input, unchanged, so a bare `/groom` never meets two questions. In auto mode the conductor dispatch and the run contract file are recognised by the skill, so an unattended worker is never parked on a question. Any other request, such as a host matching the description on a plain question, is ambiguous. For an ambiguous request the skill asks `exactly one question` ("a full run, or only an answer?"), and writes nothing tracked, posts nothing, and dispatches no worker until it is answered. A clear yes continues at step 1. Anything else (a question, silence, or a reply that is not a clear yes) means the skill answers the original question and ends, with no second clarifying question. This is a plain question, not a human decision brief, because there is no recommendation to withhold.
- **How the answer branch reads a ticket.** In groom the answer writes nothing. In draft, a question about a ticket needs the ticket text, and the only permitted way to read it is step 1's fetch command (`work-item-provider.ts read`). So the answer may run that fetch and use its result. It may save the result to `<reviewDir>/work-item.json` only when `<reviewDir>` is already ignored by the repository, so nothing tracked changes. It never runs step 1's `.gitignore` edit, never reads a provider file, never calls a remote provider directly, and never posts a note. When the folder is not yet ignored, the answer uses the fetched result without saving it.
- **Step anchors the tests rely on.** The contract test finds step 0 and the first write by exact text, not by a numbered marker, because groom's step 8 already contains `0.` and `1.` list items. In `skills/groom/SKILL.md`: step 0 is the heading `### Step 0: Confirm this is a run`, which must precede the heading `### Step 1`, and the first write is at the heading `### Step 2a`. In `skills/draft/SKILL.md`: step 0 is the line `0. **Confirm this is a run.**` and the first write is at the line `1. **Fetch the work item.**`. In each file the step 0 anchor must come first, and each anchor must exist exactly once.
- **No new stop id, verdict value, or file.** The confirmation is conversational and leaves no ledger entry, so `skills/delivery/sdlc-constitution.json` does not change. A missing or unreadable name or description fails closed as described above.
- **Existing assertions.** Step 0 does not renumber steps 1 and up in either skill, so existing step-order assertions in `factory/scripts/workflow-contracts.test.ts` are unaffected. The new assertions go in the same file, which already reads both skills.

## Test seam

- Primary: unit tests in `factory/scripts/skill-metadata.test.ts` call `skillMetadataIssues`, `hasNotForClause`, `parseSkillName`, `parseSkillDescription`, and `coveredSkillIssues` with hand-written skill text and name lists. They cover a covered skill with no clause (fails and is named), with a clause (passes, including a quoted name and a block scalar description), with a malformed or empty clause or a missing description (fails closed), an uncovered skill with no clause (not flagged), and a covered name matching no skill (reported). The existing whole-pack test in that file reads every real `SKILL.md`, so it also proves the real groom and draft descriptions carry the clause and that every covered name matches a real skill
- Contract: `factory/scripts/workflow-contracts.test.ts` reads `skills/groom/SKILL.md` and `skills/draft/SKILL.md` and asserts the `Use when` and `Not for` sentences and the example words in each description, the step 0 wording (`does not authorise a run`, `exactly one question`, the named-invocation rule, the non-yes outcome, and for draft the answer-branch fetch rule), groom's step 1 stop-and-ask text still present, and the anchor order stated above
- What it catches: a stage skill that drops or malforms its clause, a covered list entry that matches no skill or a skill renamed out of coverage, a skill file that loses step 0 or moves it after the first write
- What it misses: whether a live host or model actually stays out of the way on a plain question, recognises a conductor dispatch, and asks only one question. That is behaviour of the model reading the skill, and is not tested live. The wording is pinned so the instruction cannot vanish silently
- Boundary that needs a fake: the host and the model that match and follow the skill. Tests never load a skill into a model. They read the markdown and the script output only
- Held-out samples: none are needed, because the rule is not written from sample data

## Risks / Trade-offs

- A literal phrase rule can be satisfied by a clause that says nothing useful; accepted, because the check is a floor and the wording of the two real clauses is pinned by the contract test
- A closed covered list means a new stage skill is not covered until someone adds it; accepted, because widening coverage is a deliberate one-line change that must come with the clause, and a stale entry is reported
- A named invocation skips the question, so a person who types a command by mistake still starts a run; accepted, because typing the command is the explicit signal the ticket allows
- A skill that fails to recognise a conductor dispatch would ask the question in an unattended run; mitigated by naming the dispatch and the run contract file as named invocations in the step 0 wording, which the contract test pins

## Migration Plan

None. The check runs on the next test run after merge. Hosts pick up the new descriptions when the skills are reinstalled.
