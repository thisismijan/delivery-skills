## Context

A run's state is in four places: the ledger (`<state-root>/runs/<id>.md`), the frozen run contract (`<state-root>/runs/<id>.run-contract.json`), the OpenSpec change folder, and the next-step table in `skills/delivery/workflows/auto.md`. A new session has to find and read all of them, and it cannot tell an absent piece from one it has not looked for yet. The constitution commandment `durable-resume` says the ledger and named artifacts are the memory. This design adds one derived file that gathers those artifacts for a new session, in the same shape as `factory/scripts/review-packet.ts`, which already bundles inputs into one Markdown file.

## Goals / Non-Goals

- Goals: one standalone file per run; every piece present or named as missing; nothing the detector can see as a secret in the file; a location the status command can name; a stage-boundary moment when the conductor writes it
- Non-Goals: resuming a run from the packet; changing the ledger or run contract format; sharing the packet outside the local run; copying stops, verdicts, approvals, or lessons into it

## Decisions

- **Script and CLI:** `factory/scripts/resume-packet.ts` (new) with two modes, exported as `RESUME_PACKET_BUILD_INVOCATION` (`scripts/resume-packet.ts build <repo-root> <run-id>`) and `RESUME_PACKET_WHERE_INVOCATION` (`scripts/resume-packet.ts where <repo-root> <run-id>`). The invocation constants follow the `// biome-ignore format` single-literal pattern used by `factory/scripts/next-action.ts` and `factory/scripts/ledger-store.ts`, so the skill's wording can be tested against them. A new mode, verdict, stop id, or constitution entry is not added. The packet is a derived view written by the conductor, the same as the ledger, so no stage write kind is added and `skills/delivery/sdlc-constitution.json` is unchanged. The `status` stage keeps its empty write list, because only `where` runs there.
- **Exit codes:** 0 when `build` wrote a packet (even with gaps) or `where` answered; 1 when the run id is unsafe, or the run has neither a ledger nor a run contract, or the packet cannot be written; 2 for wrong arguments, with a usage line, as in `factory/scripts/review-packet.ts`. Gaps do not fail the build, because the ticket asks the packet to name what is missing. An unknown run fails, because a packet made entirely of gaps for a mistyped id would read as a real, empty run.
- **Run id:** the ledger's file name without `.md`, checked with the pattern `/^[a-z0-9][a-z0-9-]*$/i` that `factory/scripts/ledger-store.ts` uses, so an id cannot reach outside the state folder. The conductor already knows the id from the ledger lookup in `skills/delivery/workflows/delivery-ledger.md`, so the script does not search headers.
- **Where it is written:** `<state-root>/packets/<run-id>.md`, where the state root comes from `resolveStateRoot` in `factory/scripts/improvement-state.ts` (`<repo-root>/.delivery`, or `DELIVERY_STATE_ROOT`). It sits beside `runs/`, `candidates/`, `versions/`, and `workers/`, and `.delivery/` is already in the ignore list that `withDeliveryIgnores` in `factory/scripts/delivery-init.ts` writes to a target repo's `.gitignore`, so the packet is never tracked. It is not placed inside `runs/` because the ledger lookup there searches headers with `rg -l '^Ids:...'`; a second file with an `Ids:` line would turn one match into two, which the ledger doc makes a terminal stop. The packet therefore never starts a line with `Ids:` and uses `- Known by:` instead.
- **Exact headings:** `# Resume packet: <destination>`, then `## Missing pieces`, `## Run contract`, `## Current status`, `## Next command`, `## Decisions so far`, `## Acceptance criteria`, `## Change files`, always all present, in that order. The gap list comes first so a reader sees what is absent before the rest. The headings are the contract the test asserts.
- **How a missing piece is named:** the line `MISSING: <piece>: <reason>`, with the piece from a closed list of six names (plus ` for <key>`), written once in the piece's own section and repeated in `## Missing pieces`; `None.` when there are none. The same entries, as piece names, are the `missing` array in the stdout JSON, so a test or a script reads the gaps without parsing prose. One format is used for every gap so a person and a test find them the same way.
- **Run contract:** read with `parseFrozenRunContract` from `factory/scripts/sdlc-constitution.ts`, which already fails closed on a bad shape, a body that does not match its hash, and a contract frozen under an older constitution (`OutdatedRunContractError`). Its message becomes the reason. The packet does not run `check` against a stage and does not compare the constitution hash with the live one: that check belongs to each mutating stage, and the packet shows both hashes so a reader can see them. Acceptance criteria come from the contract's tickets (one to three per ticket), because the contract is the frozen record of what was approved. With no usable contract there is nothing to copy them from, so they are a gap too.
- **Current status:** read from the ledger's Keys table by a small parser in `resume-packet.ts`. `awaitingReview` in `factory/scripts/review-queue.ts` also reads that table, but it keeps three columns and skips rows with no change, so it cannot be reused for the full row. The new parser is strict: a missing column or a row of the wrong width is a gap with the parser's message, never a guess. It splits cells on a pipe that is not escaped and turns `\|` into `|`, the same rule as `cells` in `factory/scripts/next-action.ts` (not exported, so the rule is restated), because a title with an escaped pipe is a valid row.
- **Next command:** `selectNextAction` from `factory/scripts/next-action.ts`, called with the key as the entry and the recorded status tag. It is the one place that maps a status to a step, through the next-step table in `skills/delivery/workflows/auto.md`, so the packet cannot disagree with it. No context file is passed, so a guarded status (`[groomed]` without blocker evidence, `[executing]` without recovery evidence, an unclassified `[no-go !N]`) returns the selector's own stop reason, and the packet prints it as `no command to type yet: <reason>`. That is not a gap: the status is known and the selector answered. A `run` result prints as `/delivery <key>`, which resumes from the ledger and runs only the next legal step, with `next step: <verb>` beside it. It does not print a per-verb command, because verbs such as `review` and `ship` need an MR iid that the packet does not know. A discovery run is the one exception: its ledger key is `discover-<yyyy-mm-dd>-<slug>` (`skills/delivery/workflows/discovery.md`), and `classifyEntry` reads that as a command word with no argument and answers that it is not a known command, whatever the status. The script reuses the selector for the status lookup and special-cases only the entry: for a `discover-` key it passes the fixed stand-in entry `DISCOVER-0`, a valid ticket key, with the recorded status tag. `[discovering]` then gives `discover`, printed as `/delivery discover <key>`, which `discovery.md` names as the resume command. `[discovered]` gives `groom`, and the packet prints `next step: groom` without a command, because groom's input is the approved one-pager the ledger names and the ledger's Discovery header is not copied. `[stopped: ...]` gives the selector's own stop reason.
- **Decisions:** the bullet lines of the ledger's `## Decisions` section, verbatim. The section is append-only, so copying all of it is correct and needs no summary. A section with no bullet is not a gap; no heading is.
- **Change files:** found with `findChange` from `factory/scripts/find-change.ts`, which skips `archive` and cannot let one key select another's folder, in three places in order, and the first place with exactly one match wins. (1) The entries of `<repo-root>/openspec/changes`. (2) The key's worker worktree. An in-flight key is drafted and built in its own detached worktree (`skills/delivery/workflows/auto.md`, fan-out step 2), so its change folder is not in the repository root. No function in the repository creates or returns that path: `factory/scripts/worktree-close.ts` and `factory/scripts/sandbox-run.ts` only receive it as an argument, and the state root resolver `resolveStateRoot` in `factory/scripts/improvement-state.ts` gives the root only. So the script reads the two sources that exist: the path in the ledger's latest `dispatched <key> to <path>` Decisions line (the coordinator's own record, `auto.md` step 6, used when it is an existing absolute directory), and `<state-root>/worktrees/<key>`, the folder this repository's own draft runs use. It reads only `openspec/changes/` there and writes nothing. (3) The entries of `openspec/changes/archive`, with the leading `yyyy-mm-dd-` removed from each name (archived folders are named `<date>-<change name>`, for example `2026-10-19-generic-forge-provider`), mapping the match back to the real folder name. There is no archive-aware lookup in the repository, and this keeps the key-boundary rule and changes no existing file. `findChange` throws for a key that is not a ticket key, so a `discover-` key is skipped with its own reason and any other refusal becomes a gap with the thrown message. The Markdown files are listed and fenced by `specSections` and `fence` from `factory/scripts/review-packet.ts`, exported for this (no change in behaviour, so `factory/scripts/review-packet.test.ts` is the guard). `specSections` throws on a folder with no Markdown file, and the script turns that into the gap for that key. The files are copied in full, apart from withheld lines, because a packet handed to a session on its own cannot assume the session can read the repository.
- **Paste-safe, by exclusion first:** the script copies only the pieces above. It never copies the ledger's `Target repo:` line (which can hold a remote URL with credentials), the Discovery link, the Approvals, Verdicts, Stops, and Lessons sections, the contract's `approval` block (the operator's exact words), environment variables, lock owner records, worker journals, gate or evidence files, `.delivery.json`, or non-Markdown files in a change folder. Exclusion is stronger than any detector because it needs no guess about what a secret looks like.
- **Paste-safe, by withholding second:** the free text that remains (the ledger title and ids, Keys rows, Decisions lines, the contract's goal, scope, non-goals, ticket titles, acceptance criteria, and reason fields, the change files, and every reason string the script would show) can still carry something pasted by mistake. A recogniser of known secret shapes that copies everything else fails open on every shape its list misses, so the default is reversed here: a broad detector flags a line as suspicious, and the whole line is withheld and shown as `MISSING: <piece>: withheld because it may carry a secret; read it in <source>`, counted under `## Missing pieces` like any other gap. The detector is defined in `resume-packet.ts` and imports nothing from `provider-error.ts` or `note-publication.ts`, whose patterns were written to refuse a note and to clean one stderr line and do not suit this job. A line is suspicious for any of six reasons, written out in the spec: a key-like word followed by a colon or equals sign; user info before an at sign in a URL; a private key marker line; a known token prefix at the start of a word; a long unbroken run under rule A; or a long mixed run under rule B. The key-like words are `token`, `secret`, `passw`, `passphrase`, `pwd`, `credential`, `auth`, `api_key`, `apikey`, `api-key`, and a standalone `key`, in words that may contain underscores and hyphens, so `DB_PASSWORD=`, `X-API-Key:`, `apiKey:`, `passphrase=` and `?key=` are caught. The keyword rule is deliberately wide, so a line with `author:` is withheld too. A false withhold costs one line and one pointer to the source, while a miss costs a secret. Withholding the whole line means no partial redaction, so there is no overlap, no ordering, no count to get wrong, and no global-flag state. A private key marker withholds every line through its END marker as one block.
- **The long-run rules and what they must not catch:** counting `/` in the run alphabet would withhold ordinary repository paths such as `skills/delivery/workflows/delivery` and slash-joined word lists, so every change file would lose its path lines. Rule A is therefore 32 or more of `A-Za-z0-9+`, so a slash, dot, or hyphen ends a run and paths and word lists are never caught (a standard base64 secret with slashes in it is cut into shorter runs and can be missed, which the risks name). Rule B is 24 or more of `A-Za-z0-9_-` with a digit, an uppercase letter, and a lowercase letter, which catches base64url shapes broken by `-` or `_`, such as a 39 character `AIza` key. The uppercase and lowercase requirement goes beyond a digit and a letter, because a kebab-case change name such as `ds-5-paste-safe-resume-packet-per-run` is lowercase with a digit and would otherwise be withheld. The one exemption is exactly 64 lowercase hex characters directly after `sha256:`, the form the ledger and the constitution write hashes in. A bare 64 hex run in free text is withheld, because that is also the shape of a generated secret. The contract and constitution hashes the script writes itself are not checked at all.
- **Reasons pass the same detector:** a parser or schema message can carry contract or ledger text. `OutdatedRunContractError` in `factory/scripts/sdlc-constitution.ts` lists every human-owned string the live constitution does not know, and zod messages can include the received value. Every such reason, and the key lookup's message with its candidate folder names, goes through the detector before it is written. A suspicious reason becomes the fixed text `reason withheld because it may carry a secret`. The Keys parser is the script's own, so its messages are fixed sentences that name the problem, a column from the fixed column list, or a row number, and never quote a cell. The script's own fixed reasons are not checked.
- **Withheld title and ids:** the title line and the `Known by` line sit above the sections, so a withheld ledger title makes the title line `# Resume packet: <run id>`, and a withheld ids value makes the line `- Known by: withheld because it may carry a secret`. The run id is safe because the script's own id rule runs before anything is read. `title` and `ids` join the closed list of piece names so `## Missing pieces` and the `missing` array can name them; they have no section of their own.
- **Change files under the same rule, per line:** the change files are tracked and reviewed, but a review is not a secret scan, so each line goes through the same detector. The alternative, listing a file by path only when it must be withheld, needs a second whole-file rule and drops every safe line in the file. Per-line withholding is the smaller option and keeps the file useful, so no change file is listed by path alone.
- **What the preamble says:** only what the script does. It names the fields left out and says lines that may carry a secret are withheld and every other line is copied as written. It does not say the text is clean and does not use the word redacted, because nothing is partly redacted. A scenario pins both lines.
- **Existing files touched:** `factory/scripts/review-packet.ts` (export `fence` and `specSections`), `skills/delivery/SKILL.md` (Entry S, Stage boundaries), and `skills/delivery/workflows/delivery-ledger.md` (Location). The exports change no behaviour.
- **New files:** `factory/scripts/resume-packet.ts` (new) and `factory/scripts/resume-packet.test.ts` (new).
- **Status:** the status entry (`### Entry S`) in `skills/delivery/SKILL.md` gains one bullet that runs `where` and reports the path, and says no packet has been written when `exists` is false. Status stays read-only because `where` writes nothing and the entry never runs `build`.
- **When it is written:** the `## Stage boundaries` section of `skills/delivery/SKILL.md` is the point where the conductor decides whether a new session or worker will take over, and where the ledger is said to carry the state. The conductor writes the packet there, before Clear, a Fan-out brief, or compaction, and hands the new session the file. An isolated worker with `DELIVERY_WORKER_JOURNAL` set never writes it, because `skills/delivery/workflows/delivery-ledger.md` says a worker must not read the run ledger. The wording is the enforcement; no script refuses a worker, which is accepted below.
- **Source of truth:** the ledger doc's Location section lists the packet folder and says the packet is a derived copy, because that section also says the ledger is the only live source of run state. The packet's own second preamble line says the same to a reader who sees only the packet.

## Test seam

- Primary: `factory/scripts/resume-packet.test.ts` (new) builds fixture runs in a temporary repository and runs `resume-packet.ts` as a subprocess, the way `factory/scripts/review-packet.test.ts` runs its CLI on a temporary directory. It asserts the exit code, the stdout JSON, and the file. Fixture contracts are made with `freezeRunContract` from `factory/scripts/sdlc-constitution.ts`, so they are valid by construction, and a gap is made by deleting the file or editing a frozen body. The `.gitignore` is made with `withDeliveryIgnores` and checked with `git check-ignore`, so the ignored-path claim is tested against the real ignore list. The next command fixtures compare with `selectNextAction` called directly, so the packet is checked against the selector instead of a copied table.
- Paste-safe: the fixture plants, one per detector, a value of a shape that a short list of known secret patterns would miss: `DB_PASSWORD=...`, a quoted JSON `"password"` key, an `Authorization: Bearer` line with a JWT, `apiKey:`, `X-API-Key:`, `passphrase=`, a `?key=` link, `ghs_`, `glrt-`, `AKIA...`, an `AIza` style 39 character key, a URL whose only user info is a token, a bare 40 character base64 run, a bare 64 hex run, and a PGP private key block. The test asserts each planted line is replaced by the `MISSING:` line, that the value is absent from the file, that a clean line next to them is copied, and that the `missing` list counts each withheld line once. The complete-run fixture plants what must not be withheld: a repository path of more than 32 characters, a slash-joined word list, a kebab-case change name with a digit, and a `sha256:` hash. A second fixture plants a value in the contract's goal, a scope item, an acceptance criterion, a Keys title, the ledger title, the ids, and a change file line. A third makes a contract and a Keys table that fail to parse with planted values in the parser's message. A fourth plants a plain sentinel in every excluded field. Worker worktree fixtures are plain temporary directories, and the test asserts nothing under them changes. Because withholding is per line and not by pattern replacement, no regex with a global flag is shared between lines.
- Wording: the same file reads `skills/delivery/SKILL.md` and `skills/delivery/workflows/delivery-ledger.md` and asserts the status entry and stage boundary wording against the exported invocation constants, and that the status entry does not contain the build invocation.
- What it catches: a missing or misordered heading, a gap dropped or unnamed, a gap that stops the build, a suspicious line, reason, or sentinel field reaching the file, a clean line or a path withheld by mistake, a wrong next command for a discovery key, a change in a worktree or the archive reported missing, a preamble that promises more than it does, a packet outside the ignored folder, a packet with an `Ids:` line, a next command that differs from the selector, a status step that writes, a skill that drops a rule
- What it misses: a secret that none of the six reasons flags (a short value with no key word, for instance a bare password in prose), and whether a new session, handed only the packet, actually continues the run well. That is model behaviour and is not tested live
- Boundary that needs a fake: none. Everything is local files and a subprocess; no model, network, or forge is called
- Held-out samples: none are needed, because no rule is written from sample data. The planted secret values are fixtures for patterns that already exist

## Risks / Trade-offs

- The packet is a copy and can go stale between stage boundaries. Mitigated by its own warning line, by the ledger staying the source of truth, and by `build` being cheap enough to run again
- Copying every change file makes the packet long for a large change. Accepted so the packet stands alone; the person handing it over can trim it, because it is one Markdown file
- A secret that matches none of the six reasons is still copied, for example a standard base64 value whose slashes cut it into runs under 32 characters, or an all lowercase base64url value. Accepted, and the preamble does not promise otherwise; the exclusions are the first defence and the wide detector the second
- The detector over-withholds: a line with an ordinary word such as `author:`, or a 40 character git SHA (only a `sha256:` prefixed 64 hex hash is exempt), is withheld and shown as a gap. Accepted as the safe side of the trade; the source is one pointer away. Whether to exempt 40 hex SHAs is an open question below
- The stops recorded in the ledger are not in the packet, so a stopped key shows the selector's reason and not the next command its Stops line recorded. Accepted because the ticket lists six pieces and the ledger remains one file away; the first open question below asks whether to add them
- The worker worktree path is a convention (the dispatched line, or `<state-root>/worktrees/<key>`), not an enforced location. A worktree kept elsewhere with no dispatched line is reported as a gap
- A worker could run `build` against the run ledger. Accepted because the wording forbids it and a refusal would need a new signal; the packet only reads
- A second copy of the Keys table parser exists next to `awaitingReview`. Accepted because the two read different columns for different rules

## Migration Plan

None. A run with no packet reports that none has been written, and the next stage boundary writes one.

## Open Questions

- Whether the packet should also carry the latest Stops line for a stopped key. The ticket does not list it, so this design leaves it out
- Whether a 40 hex git SHA should be exempt like the `sha256:` hash. Ledger entries write SHAs in full, so Decisions lines with a SHA are withheld until one is, but 40 hex is also the shape of an old GitHub token
