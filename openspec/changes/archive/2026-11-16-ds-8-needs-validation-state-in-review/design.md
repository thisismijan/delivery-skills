## Context

Adjudication in `skills/code-review-max/SKILL.md` has one rule that ends a candidate's life without telling anyone: step 7, "Downgrade or drop a finding whose impact or trigger cannot be shown". A risk that is real in the code but depends on a fact outside the repository (a replica count, a production setting, a deployment topology) falls under it, so the operator never hears about it. Release readiness also cannot ask for the fact, because it decides GO or NO-GO from findings that have a severity.

Findings from reading the repository, which shape the decisions below:

- **Readiness is decided in prose.** `factory/scripts/readiness-decision.ts` exports `decideReadiness`, but no non-test code imports it. `skills/delivery/workflows/release-readiness.md` step 6 lists the NO-GO reasons in words and the conductor, a model, applies them. A gate added only as wording would be unenforced. The workflow already does run real commands for other gates (`scripts/stage3-readiness.ts`, `scripts/reviewer-settle.ts`), so the gate gets a command of the same kind, and `decideReadiness` is given the same rule so the two cannot disagree.
- **Stage 3 reads the review text by regular expression.** `parseMax` in `factory/scripts/stage3-readiness.ts` tests the whole body of the code review against `/\[(Critical|High|Medium)\]/i`, and `approachFindingsBlock` treats any line holding `[bug]`, `[approach]`, or `[nit]` as a finding. A needs-validation item that quotes a severity word, which it naturally might ("if two replicas run, this is a [High] risk"), would be read as a blocker, which is the opposite of what the ticket wants. The parser therefore needs explicit support, not an assumption that the item will be worded carefully.
- **The ledger has no structured acknowledgement.** Approvals lines are free text after a UTC time (`factory/scripts/ledger-store.ts`, `isLedgerTime`, from DS-6). `land-gate.ts` and `ledger-store.ts` each read a section on their own, and a third copy would drift. The writer already accepts any timed bullet in Approvals, so an acknowledgement needs a line shape and a reader, not a writer change.
- **Items outlive a head.** Reviews are stamped per head, but the ticket scopes an acknowledgement to the merge request. An item raised at one head has to be recognisable at the next, so its id cannot come from a line number, a position, or a head.
- **Second-pass publication turns text into comments.** `skills/mr-review/SKILL.md` posts each anchored finding as its own note, and release readiness counts every comment the run did not publish itself as unanswered. An item published as a note would be answered or counted as a comment blocker, which is the wrong gate.

- **Auto's NO-GO route is chosen in code.** `factory/scripts/next-action.ts` decides the next step for `[no-go <x>]` from `noGoNext`, a closed set of `address`, `wait`, and `risk-acceptance`. Anything else, or nothing, stops with "Classify the NO-GO blocker". An open item fits none of the three: `address` would send it to a loop that has no code fix, `wait` would poll for something nothing will change, and `risk-acceptance` is the wrong gate. Wording in `auto.md` alone would leave the conductor to pick the nearest value.
- **A review that has an earlier review does not always review a delta.** `factory/scripts/review-scope.ts` returns `full` for the max level, for a change that touches a sensitive surface, and whenever the delta is large, and `skills/code-review-max/SKILL.md` adjudication mode `none` writes "No findings." with nothing to verify. Readiness reads only the `max.md` at the live head, so a carry-forward rule held only in the delta text lets an item leave the gate in the other paths.
- **A worker may not read the run ledger.** An isolated auto worker has `DELIVERY_WORKER_JOURNAL` set, writes only its own journal, and never touches the shared ledger (`skills/delivery/SKILL.md`, `skills/delivery/workflows/delivery-ledger.md`, `auto.md`). The coordinator is the only writer of the run ledger. So the gate must say which ledger it reads and who records an acknowledgement.
- **The review text is Markdown, and Markdown has fences.** `section` in `factory/scripts/next-action.ts` already skips headings inside a fenced block. A section reader that does not will end an item early on a `# ` comment in a shell snippet and then scan the rest of the item as ordinary review text.

DS-6 (UTC time on every new Stops and Approvals line) is already in the tree, so the acknowledgement line starts with the time form it requires. DS-5 (resume packet) reads the ledger and is not changed here: an acknowledgement is an ordinary Approvals line.

## Goals / Non-Goals

**Goals:**
- Keep a risk that depends on an outside fact, with the exact missing fact and a safe owner check, instead of dropping it
- Never give it a severity, and never let it set `BLOCK`, so a review with only such items still passes
- Make release readiness NO-GO until the ledger holds an acknowledgement for each item, decided by code that tests can run
- Keep an item recognisable across pushes and review rounds, so an acknowledgement is neither orphaned nor asked for twice
- Keep items out of the blocker regexes, out of the merged finding set, and out of the comment scoping

**Non-Goals:**
- Severity for an item, probing live environments, running the owner check, remembering disproved candidates (slice 9), lens coverage (slice 10)
- Closing an item because the owner ran the check. Only an acknowledgement, or the disappearance of the code that raised it, ends the gate
- Any change to the holdout review, `factory/scripts/verdicts.ts`, `factory/scripts/review-summary.ts`, or `factory/agents/first-pass-reviewer.md`. The affected-area list named them. They validate an execute round and a drafted change, carry no adjudicated candidate, and have no place for this state, so changing them would widen a type for no behaviour

## Decisions

**These seams are the chosen design. The run is `continuous-delivery: yes`, so the implementer builds them as written and does not re-ask.**

### The outcome and where it lives

- **Third adjudication outcome.** `skills/code-review-max/SKILL.md` adjudication step 7 keeps the old rule: a finding whose impact or trigger cannot be shown is downgraded or dropped, unless step 8 applies. Step 8 is new: a candidate is kept as **needs-validation** when the code at the head shows the bad behaviour, the harm depends on one named outside fact, the adjudicator searched the repository for it (configuration, manifests, CI deploy jobs, runbooks, `design.md`) and did not find it, and the adjudicator can write down the fact and a check. If the repository does show the fact, the candidate is judged by it. If any condition fails, the candidate is dropped under step 7 as before. Step 8 keeps the guard against manufactured doubt: "I am not sure" is not a missing fact.
- **No severity, no `BLOCK`.** The Severity section says a needs-validation item carries none. The lens candidates keep their severities, and the severity counts in `lens-candidates.json` and the adjudication mode are measured before adjudication, so nothing in the fan-out changes. The verdict rule becomes: `BLOCK` only for a Critical, High, or Medium finding, or several Low findings with one root cause.
- **Owner check is read-only and written, never run.** The skill says the check names where the owner looks (for example, "read the replica count for this service in the deploy dashboard") and never asks the reviewer, or the factory, to probe a live environment. This is the "safe check" of the ticket and the line that keeps probing out of scope.
- **Output section.** After `### Findings` and before `### Verification`, the template gains `### Needs validation`, omitted when empty. With no finding and one item, `### Findings` says `No findings.` and the verdict is `PASS`.

```markdown
### Needs validation

1. **`path/file.ts` — <short title>**
   **Missing fact:** <the exact fact the repository cannot show>.
   **Owner check:** <a safe, read-only check the owner can run to settle it>.
```

- **Heading constant.** `factory/scripts/needs-validation.ts` (new) exports `NEEDS_VALIDATION_HEADING` (`### Needs validation`). The parser, the contract tests, and the template all derive from it. A test reads it and asserts both skill templates contain it.

### Stable item id

- `needsValidationId(path, missingFact)` returns `NV-` plus the first eight lowercase hex characters of the SHA-256 of `<normalized path>\n<normalized fact>`. Path normalization: trim, drop a leading `./`. Fact normalization: trim, collapse whitespace runs to one space, lowercase, strip trailing `.`, `;`, `:`.
- **Code computes it, the reviewer does not write it.** A model cannot hash by hand, and a hand-written id could drift. The id is never in `max.md`. It first appears in the output of the command (below), so it first reaches the operator in the readiness brief, which is where they need it.
- **Why path and fact, not title, line, or head.** Line numbers and heads change on every push, titles are reworded, and list position changes. The path and the missing fact are what the item is about. A review that finds the same risk copies the earlier missing fact unchanged (the carry-forward rule says so), so the id holds.
- **Alternative rejected: a reviewer-chosen label**, as address-comments does for an assumption. Rejected because a label is a second thing for a model to keep consistent across rounds, and a collision or a reword silently orphans an acknowledgement. A derived id fails the same way only when the fact is reworded, and then it fails closed: the old acknowledgement is ignored and the item is open, so the gate stays NO-GO and the brief shows the new id.
- **Orphaned acknowledgements are ignored**, never an error. An item that a later review closes under `### Earlier findings` leaves the set.

### The parser and the command

New file `factory/scripts/needs-validation.ts` (new), with these exports:

- `NEEDS_VALIDATION_HEADING`, `NEEDS_VALIDATION_ACK_PHRASE` (`acknowledged needs-validation`), and `NEEDS_VALIDATION_CHECK_INVOCATION` (`scripts/needs-validation.ts <iid> <head> <max-pass> <ledger> <previous-max-pass>`, written as one double-quoted literal under the same `biome-ignore format` comment the other invocation constants use, so the contract tests read it)
- `splitNeedsValidation(markdown): { rest: string; sections: string[] }`. A section starts at a line equal to the heading, ignoring case and trailing space, at column 0, and ends at the next line that starts a Markdown heading (`#` to `######` then a space) or begins `<!--`. **The reader is fence-aware**: it tracks fenced blocks (three or more backticks or tildes, closed by the same character), so a heading line inside a fence outside a section neither starts nor ends one. A code block that opens inside a section is a problem, because an item is one line for its missing fact and one line for its owner check, and the text from its opening line to the end of the review is left in `rest`, where the blocker checks read it, so a code block can hide no finding. The reader does not share code with `next-action.ts`, which reads one fixed heading and returns text. Pulling both into one reader is a refactor of another file and is not needed to get the behaviour. `sections` holds the lines inside. `rest` is the markdown without them, except for a **misplaced finding**: any line inside a section, numbered, bulleted, quoted, indented, or a plain paragraph, that contains one of `[Critical]`, `[High]`, `[Medium]`, `[Low]`, `[bug]`, `[approach]`, `[nit]` (case-insensitive, fenced lines included). That line, with its continuation lines up to the next list marker or blank line, stays in `rest`. Where lines were taken out of the section, the heading `### Needs validation` is inserted into `rest` before the next kept line, so a finding cannot continue across the gap. The label counts wherever it sits in the line, not on numbering, so an item that quotes "[High]" in a sentence keeps the merge request draft; that is the cost of a finding that cannot hide by where it is placed. A heading that is not the exact heading (for example `## Needs validation`) is not recognised, so its text is scanned as before. That fails closed.
- `parseNeedsValidationItems(markdown): { items: NeedsValidationItem[]; problems: string[] }`. A severity label or finding tag that moves a line out of the section is a problem whatever its severity, so an item carrying one is never dropped silently. An item head is a numbered line, `` 1. **`path` — title** ``, followed by a `**Missing fact:**` line and an `**Owner check:**` line, each non-blank, each continued by following indented lines. Every numbered entry in a section that is not an item head (a missing path), every non-blank line before the first item head, every line that is not an item head, a `**Missing fact:**` line, an `**Owner check:**` line, or a continuation of one of them, and a code block is a problem, as is an item with no missing fact or no owner check. Nothing in the section is ignored. Problems are plain sentences and name the entry's title. Items with the same id are merged into the first.
- `needsValidationId(path, missingFact): string` as above
- `parseClosedNeedsValidation(markdown): { closed: NeedsValidationItem[]; problems: string[] }`, which reads the numbered entries of the `### Earlier findings` section whose first line is `` `path` — closed: <title> `` followed by a `**Missing fact:**` line, with the same fence-aware reading, and gives each the id of its path and fact
- `needsValidationAcknowledgements(ledger: string): NeedsValidationAcknowledgement[]`, which reads every Approvals line through `sectionEntries` and keeps those that match `^- (\S+) !(\d+) — acknowledged needs-validation (NV-[0-9a-f]{8}) — (.+?) — "(.*)"$`, whose time passes `isLedgerTime`. Lines that do not match are ignored, never errors, because the section holds other approvals
- `checkNeedsValidation({ iid, head, maxPass, ledger, previousMaxPass, workerJournal })`, the pure core of the command, which returns `{ items, closed, open, problems, ledgerRead }` and uses `openNeedsValidation` from `factory/scripts/readiness-decision.ts` to decide openness

The command is `if (import.meta.main)` in the same file, the pattern every other script uses. `<ledger>` of `-` means an empty ledger. It prints the JSON object with every printed text passed through `sanitizeHumanText`, and exits 0 (nothing open, no problem), 1 (open), or 2 (problem or unreadable input).

**Bound to the review of this head (fail closed).** The command is given the live head as well as the merge request number, and before it reads an item it checks the file: not empty, a last non-blank line that matches the max marker `<!-- code-review-max:mr=<iid> head=<head> -->` for that number and that head, and a verdict. `MAX_MARKER` in `factory/scripts/stage3-readiness.ts` gains `export` (one word, as `sectionEntries` does) so the command and stage 3 read the marker with one pattern. An empty, stale, other-merge-request, or other-head file exits 2 and never 0. Stage 3 already checks the same three things for its own gate. The command checks them again because it can be run on its own, and exit 0 means "nothing open in the review of this head", which a wrong file cannot truthfully say. The head is passed as an argument. The command does not run git.

**Earlier items are checked by the command (fail closed).** `<previous-max-pass>` is the earlier review that `review-scope.ts` names as `previous`, or `-`. An earlier item whose id is neither among the items nor among the closed items of the review at the head is a problem and exits 2. Each review is checked against the one before it, so the chain holds over any number of pushes: an item closed in one review is no longer owed by the next. The command cannot check that a closure is true. It checks that an item is never dropped without a line that says why, which is the part a model drops silently. All five arguments are required, so leaving out the earlier review is a usage error rather than a silent skip, and the readiness workflow reads `previous` from the pinned `review-scope.json`.

**Worker mode.** When `DELIVERY_WORKER_JOURNAL` is set, the command reads no ledger, every item is open, and the output carries `ledgerRead: false`. See "Workers" below.

`factory/scripts/ledger-store.ts` changes by one word: `sectionEntries` gains `export`. (`MAX_MARKER` in `stage3-readiness.ts` gains the same word.) Reusing the writer's section reader, which already handles heading case, whitespace, carriage returns, and repeated headings, avoids a third reader that drifts. `ledger-store.ts` starts its command only under `import.meta.main`, so importing it from a parser has no side effect.

### Readiness decision

- `factory/scripts/readiness-decision.ts` gains `NeedsValidationItem`, `NeedsValidationAcknowledgement`, and `openNeedsValidation(iid, items, acknowledgements)`. An acknowledgement applies when its merge request number equals `iid`, its item id equals the item's id, and both `acknowledgedBy` and `words` are non-blank, the same `recorded` test the existing acceptance uses. The head is not compared. An absent `iid` with items present leaves every item open.
- `ReadinessInput` gains three optional fields, `iid`, `needsValidation`, and `needsValidationAcknowledgements`, and `ReadinessDecision` gains `awaitingAcknowledgement`. **Optional on purpose:** every existing call and test stays as written, and no existing test is edited. The decision is `NO-GO` when `blocking` is non-empty or `awaitingAcknowledgement` is non-empty. An item is never put in `blocking` or `accepted`, because those carry a severity and an acceptance by head, and the two clearing paths must not overlap: an acceptance cannot clear an item and an acknowledgement cannot clear a finding.
- **Why optional fields on `decideReadiness` and also a command.** The conductor is a model, so a pure function with no entry point stays unenforced, which is today's state for security findings. The command is the entry point for this gate. `decideReadiness` keeps the full rule for any caller that wires it later, and both call `openNeedsValidation`, so there is one rule. Wiring the security findings into a command is a separate change and is not done here.

### Stage 3 reads the section as non-blocking

- `factory/scripts/stage3-readiness.ts` calls `splitNeedsValidation` on each review body (the one reader, so stage 3 holds no second copy of the fence and label rules) and runs its existing checks on `rest`, so `MAX_BLOCKING_SEVERITY` and `approachFindingsBlock` never see the prose of an item. The verdict, marker, and head checks are unchanged and read the same text as before.
- Order in `parseMax` and `parseApproach`: marker, verdict, then the earlier findings problems (a code block there, or a closed entry with no missing fact, keeps the draft), then the blocker search, then the item check. The earlier findings problems come first because a problem there can hide later text from the blocker search. A review that has a real blocker reports "still has blockers"; only a review that would otherwise be ready reports the incomplete item, with the plain reason "The max-pass review has an incomplete needs-validation item." (and "approach-pass" for the second pass).
- One reader for the earlier findings section: `walkEarlier` in `factory/scripts/needs-validation.ts` tracks fences on every line and classifies each line as text or closed fact. A code block opened inside a closed (`closed:`) entry is a problem; an ordinary earlier finding may hold a code block, and it does not block readiness. `parseClosedNeedsValidation` and `withoutClosedFacts` both take their answer from that walk, so the closed items and the text searched for blockers cannot come from two readings of the earlier findings section. `parseClosedNeedsValidation` walks the whole body; `withoutClosedFacts` walks the body outside the needs-validation section, which is what stage 3 searches.
- **Alternative rejected: a `needs-validation` marker word that the regex excludes.** A word list is what already fails when an item quotes a severity. Structure (a heading section) is robust to what the item says.
- **Alternative rejected: ignoring the section entirely.** That would let a finding hidden in it pass. The misplaced-finding rule keeps the guard the existing parser had.

### The second pass

`skills/mr-review/SKILL.md` Phase 5 gains rules: needs-validation items from the accepted `max.md` are carried through unchanged in substance under the same heading; they are not tagged, not counted in the nit cap, not in `### Findings`, and get no `NN-<slug>.md`. The summary template gains the section. Because no note is anchored to an item, nothing for it reaches `forge-comments.ts` scoping, and precondition 6 of readiness cannot count it. The `summary.md` note is already published by the run and already excluded from "unanswered".

### The readiness gate

- `skills/delivery/workflows/release-readiness.md` step 6 gains a NO-GO bullet and a command: run `bun "${FACTORY_ROOT}/scripts/needs-validation.ts" <iid> <head> <max-pass> <ledger> <previous-max-pass>` against the pinned code review at the live head, the run ledger, and the earlier review that the pinned `review-scope.json` names as `previous` (`-` when it names none). Exit 1 is a NO-GO reason; exit 2 stops the stage with "the review has an incomplete needs-validation item; run `/delivery review <iid>`". Step 7's brief gains `### Facts to confirm before merging` and `### Facts acknowledged`. The checkpoint table gains a row: the operator acknowledges an item, the stage appends the Approvals line, recomputes, and reissues the brief. Ledger writes: each acknowledged item goes to Approvals and the open count goes to Decisions.
- **Where the command reads items from.** The pinned `max.md` for the live head, because stage 3 already requires one that matches the head, and the carry-forward rule (every scope and mode) carries earlier items into it. The second-pass summary is a human copy, not a second source.
- **Who writes the acknowledgement.** Only on the operator's own words in the conversation, as for any approval in `delivery-ledger.md`. The line is
  `- <yyyy-mm-ddThh:mm:ssZ> !<iid> — acknowledged needs-validation <id> — <who> — "<operator's words>"`.
  The scope is the merge request, as the ticket says. `delivery-ledger.md` Approvals rules gain this line and say that `continuous-delivery: yes` never authorizes it. The existing scope rule already says a head-scoped approval does not cover another scope, so a risk acceptance cannot be read as an acknowledgement.
- **Meaning of an acknowledgement.** It records that the owner saw the fact and the check. It is not proof that the risk is gone, and the brief says "acknowledged by", never "resolved".
- **Auto, in code.** `noGoNext` in `factory/scripts/next-action.ts` gains a fourth value, `acknowledgement`, in the `NextActionInput` type and in the `NextActionContext` schema. For `[no-go <x>]` it returns the same stopped result the `risk-acceptance` value returns, with its own plain reason: "Release readiness needs the operator to acknowledge a fact to confirm before merging." It never returns the address action or a wait. The three existing values and the stop for a missing classification are untouched. **Why a value and not a reuse of `risk-acceptance`:** the two gates have different evidence (an Approvals line scoped to the merge request, against a head-scoped acceptance), and a shared value would make the stop reason wrong for one of them. **Order:** when an item is open beside a comment or code blocker, the conductor classifies `address`; the fix loop ends in another readiness run, which reaches `acknowledgement` once the item is the only reason left. Choosing `acknowledgement` first would leave a fixable blocker waiting for a person. `skills/delivery/workflows/auto.md` states this for the `[no-go !N]` row and the list of reasons auto asks about, and tells the conductor to take `acknowledgement` from exit 1 of the command. The helper stays pure, so the conductor still supplies the classification. This change fixes what the choices are, which is where the gap was.
- **Not in the constitution's stops.** No new stop id is added. A NO-GO is a verdict, and the existing "operator-owned" path already covers waiting for a person.

### Carry-forward in every scope and mode

The rule is not part of the delta text. `skills/code-review-max/SKILL.md` states it once, in a place every path reads, and the delta, full, and no-candidate text point to it. A review of a merge request with an earlier review accounts for every needs-validation item of the most recent earlier review, in one of two ways: listed again under `### Needs validation` with the path and the missing fact copied unchanged, or closed under `### Earlier findings` as `` N. **`path` — closed: <title>** `` with the unchanged `**Missing fact:**` line, where the title says whether the code is gone or the repository now shows the fact.

- **Rebased earlier review.** A rebase rewrites the earlier head, so that head is no ancestor of the head under review. `review-scope.ts` names the most recent earlier review as `previous`, with scope `full` and a reason that says the whole change is reviewed against it, so the items are carried or closed against the review that really came before. The most recent review is the one with the newest commit time, and a tie goes to the review written later. When it is not an ancestor, it is named even when an older earlier review is an ancestor, which is the case of an amended head. A merge request with no earlier review at all remains a first review. This is the only case where a `full` scope names `previous` from a non-ancestor. A candidate whose commit the clone no longer holds is ordered by the modification time of its review file, so it is still named and never dropped.
- **Full scope.** A full review re-adjudicates the whole change, and its adjudicator could raise the same risk again with a reworded fact, which would change the id and orphan an acknowledgement. The skill therefore tells it to start from the earlier items: copy the fact unchanged when the risk stands. `review-scope.ts` gives it the head of the earlier review as `previous` in both scopes (it already holds `previous.head` and returns it as `since` for delta only). That is a one-field addition to the full result, and no scope decision changes. The earlier review is also given to the lenses in a full scope review, as the delta text already does, so a lens can see what was already kept.
- **Mode `none`.** "Nothing to verify" now applies to lens candidates. The skill says the review still writes the carried and closed items. A first review, with no earlier items, behaves as before.
- **Mode `standard` and the rest.** The adjudicator receives the earlier items in its packet.
- **What checks it.** The skill text is model-run, but the command compares the review at the head to `previous` and exits 2 when an earlier item is neither listed nor closed. The residual risk is a false closure, written for an item whose code still stands. It is not mechanically checkable here, and it is visible: the closure is a line in the review that the second pass and the operator can read.
- **Alternative rejected: rebuild earlier items from the earlier review in code and merge them into the output.** That would make the helper write review text and hide the carry-forward from the reviewer, so a changed fact could never be noticed. Checking after the fact keeps the reviewer in charge of the wording and the gate in charge of the result.

### Workers

An isolated auto worker never reads or writes the shared run ledger. For this gate:

- The command, given `DELIVERY_WORKER_JOURNAL` in its environment, reads no ledger and reports every item open with `ledgerRead: false`. A worker therefore cannot look like it holds an acknowledgement it was never allowed to see, and a ledger path passed by mistake cannot clear the gate.
- A worker stops at an open item and reports each item's id, missing fact, and owner check in its result. The coordinator asks the operator, writes the acknowledgement to the run ledger only on the operator's own words, and recomputes the gate against the run ledger.
- A worker never writes the acknowledgement phrase, and the coordinator never copies a line containing it from a journal when it reconciles. It reads the worker's open items as evidence. `skills/delivery/SKILL.md`, `delivery-ledger.md`, and `auto.md` each carry the rule, pinned by a contract test that reads the phrase from the code.
- **Alternative rejected: refuse an acknowledgement line in `ledger-store.ts` when `workerJournal` is true.** It is the strongest enforcement, since it stops the write, but `ledger-store.ts` would have to import the phrase from `needs-validation.ts`, which already imports `sectionEntries` from `ledger-store.ts`, so the two files would import each other for one constant. Reading side enforcement plus the reconcile rule closes the same hole: a line in a journal never reaches the run ledger, and the command never reads a journal as a ledger.

- **What it catches:** an item dropped; an item given a severity or setting `BLOCK`; an item quoting a severity word that blocks; a finding hidden inside the section that passes; an incomplete item that reaches readiness; an item dropped by a full, delta, or no-candidate review; a stale, empty, or wrong-head `max.md` that exits 0; an unnumbered or fenced finding hidden in the section; an open item routed to the fix loop; a worker journal clearing the gate; an acknowledgement matched across merge requests, across ids, by head, or without who or words; an acknowledgement orphaned by a reworded title or a moved line; a standing approval or a risk acceptance clearing an item; an item published as a note; a heading or phrase in the markdown that drifts from the code; the command and the pure decision disagreeing.
- **What it misses:** whether the adjudicating model keeps an item instead of dropping it, whether it copies the missing fact unchanged in a later round, and whether a closure is true. The markdown rules are pinned, the parser rejects a malformed item loudly, and the command catches an item that is neither listed nor closed, but no test runs a live model, and a false closure passes the command.
- **Boundary that needs a fake:** none. The parser, the decision, and the command are local and deterministic, so tests use real strings and temporary files.
- **Held-out samples:** none are needed. The rules come from the ticket, not from sample data.

## Risks / Trade-offs

- **A malformed earlier review stops one push, and its items are not checked past that push.** When the earlier review has a problem (for example a code block in its section), the command reports it as "In the earlier code review: ..." and exits 2 at the head it checks. The stop does not repeat at the next push by itself: `review-scope.ts` then names the newest review file, which is the stopped head's review, so the next push is checked against that review and not against the malformed one. The items the malformed review held are therefore not checked by that push, and the stop message does not name the earlier head. This fail-open across one push is recorded as an open decision for the operator: whether a stopped head must be reviewed and cleared before the next push, and how that is recorded. This change does not decide it.
- **A review that omits an earlier item could remove it from the gate.** Readiness reads one `max.md`. Mitigation: the carry-forward rule applies to every scope and mode, and the command takes the earlier review and exits 2 when an earlier item is neither listed nor closed. Residual: a false closure is still model-run, and the chain is only as good as the earlier review being the true `previous`. The cost is one more argument and one more field in the scope output.
- **Rewording a missing fact changes the id and re-opens an acknowledged item.** This fails closed, and the brief shows the new id. The cost is one more acknowledgement. Normalization and the copy-unchanged rule keep it rare.
- **A model may keep a weak candidate as an item to avoid deciding.** The three conditions (shown behaviour, one named outside fact, repository searched) and the plain requirement of an exact fact and a check are the guard, and an item the operator finds empty can be acknowledged in one line. Trade-off accepted: a visible small cost beats a silent drop.
- **An acknowledgement is not proof.** An operator can acknowledge without running the check. The ledger records who and their words, so it is auditable, and it matches how risk acceptance already works.
- **The decision helper gains optional fields instead of a new required shape.** This keeps every existing test as written and leaves the old calls alone. The cost is two ways into the rule (the helper, the command), kept equal by one shared function.
- **Overlap with other ledger work.** DS-6 is in the tree and already defines the time form this line uses. DS-5's resume packet reads Approvals as plain lines and needs no change. A later change that adds structure to Approvals must keep `acknowledged needs-validation` lines readable, and the contract tests that read the phrase from the code will say so.
- **The command has five required arguments.** Passing `-` for the ledger or the earlier review is a choice the workflow makes visible, and a missing argument is a usage error, so no skipped check can look like a pass. The cost is a longer invocation.
- **Markdown edits across six skill and workflow files.** Each one is pinned by a test derived from the code, so wording cannot drift without a failure, and no existing assertion is weakened.

## Migration Plan

None. Reviews written before this change have no section, so the command exits 0 for them and stage 3 reads them as before. A ledger needs no edit. The first review after merge that finds an outside-fact risk produces the first item.

## Open Questions

None blocking. Two choices were made so that the implementer does not have to ask: the id is derived from the path and the fact, and the acknowledgement is scoped to the merge request alone, as the ticket states.
