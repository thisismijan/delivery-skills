## Context

`/code-review-max` fans out read-only lenses, then adjudicates every candidate they return (`skills/code-review-max/SKILL.md`, "Adjudicate every candidate"). Adjudication drops duplicates, claims already raised, claims resting on a name or comment, and claims whose impact cannot be shown, and disproves others by reading the code, running a reproduction, or finding an existing guard. The dropped candidates are not written anywhere. The only state a later review reads is the earlier head's `max.md`, which `review-scope.ts` uses to choose a delta review, and which holds findings only. So a candidate that adjudication disproved is raised again by a lens the next time the merge request is reviewed, on code nobody touched, and the operator dismisses it again.

Two facts shape the design. First, a lens candidate has no title: the lens brief lists severity, `path:line`, the bad behaviour, a trigger, evidence, a fix direction, and the rule it violates, and each review's lenses word the same claim differently. A rule that needs two candidates to share a normalised title would almost never match in real use while every unit test passed. Second, the adjudicator already reads every candidate and the code it cites, and it is the only reader able to say whether two differently worded candidates describe the same bad behaviour.

So the work is split by what each side can decide. A deterministic script decides the question it can answer exactly: is the code a remembered rejection cited still present, unchanged, at the place this candidate points to? The adjudicator decides the question only a reader can: is this the same claim? A script never suppresses a candidate, so a wrong earlier rejection can only cost a wrongly dropped candidate through the adjudicator's own comparison, which is shown to the operator.

The delivery scripts already follow one shape for this kind of state: a deterministic script under `factory/scripts/` that holds the rule, a zod schema for any file it writes, a pair of exported invocation strings that the skill markdown copies and `factory/scripts/workflow-contracts.test.ts` compares with the script's own exports, and a skill step that calls it and stops the stage on a non-zero exit. `review-rounds.ts` keeps a versioned JSON file with that shape. `review-scope.ts` reads `.review/mr-<iid>/<sha>/max.md`, shells out to `git`, and treats a merge request id as digits and a head as a full SHA. This change reuses those conventions and changes neither script.

`.review/` is gitignored and local to a worktree. Delta review has the same limit, so the memory inherits it and says so.

## Goals / Non-Goals

- Goals: remember a disproved candidate with its reason and cited code, across reviews of the same merge request; tell the adjudicator, deterministically, when a candidate points into code a remembered rejection cited that has not changed, with the remembered title and reason; let the adjudicator drop the same claim without re-investigating it; force a fresh judgement whenever the cited code changed; show what was dropped; leave every other candidate and every other merge request exactly as before; give `record` real input in every adjudication mode; one deterministic rule that a test can prove without a model
- Non-Goals: tracking fixed findings; memory across merge requests; the needs-validation state; deciding in a script whether two claims are the same; carrying memory to another clone or runtime; changing scope selection or how `mr-review` merges findings

## Decisions

- **Script and commands:** `factory/scripts/review-memory.ts`, with two commands.
  - `record <repoRoot> <iid> <head-sha> <outcome.json>`
  - `filter <repoRoot> <iid> <head-sha> <candidates.json>`

  The script exports `REVIEW_MEMORY_RECORD_INVOCATION` and `REVIEW_MEMORY_FILTER_INVOCATION`, the usage strings in that form, written as one double-quoted literal each under the same `biome-ignore format` comment `review-scope.ts` uses. It also exports the functions the tests call: `normaliseCode`, `locateCode`, `locationKey`, `rejectionRef`, `recordOutcome`, `filterCandidates`, the `ReviewMemory` schema, and `REJECTIONS_BUDGET_CHARS`. The script exits 0 on success, 1 when its arguments, the repository, or a memory or filter file are unusable, 2 on a missing argument, and 3 when `record` refuses the outcome file. Exit 3 is the only code a skill may recover from. The usage line is printed on a missing argument with exit 2, as the other scripts do. `filter` is named for what the skill calls it, but it only reports; it removes nothing.
- **Where the memory lives:** `.review/mr-<iid>/rejected.json`, directly under the merge request's directory and not under a head directory. A head directory belongs to one pinned review and `review-scope.ts` lists the directories whose names are full SHAs, so the file must not be shaped like one. The path is built from `repoRoot`, the digits-only `iid`, and a fixed name, so nothing in a candidate can choose where it is written.
- **Schema:** zod, strict, versioned. An entry is one place in one file, and holds the rejections made there.

  ```json
  {
    "version": 1,
    "entries": [
      {
        "path": "src/parse.ts",
        "code": ["normalised line", "..."],
        "rejections": [
          {
            "title": "Parse crashes on empty input",
            "reason": "The caller rejects empty input before parse is reached.",
            "recordedHead": "<40 hex>",
            "startLine": 10,
            "endLine": 14,
            "guards": [
              { "path": "src/caller.ts", "code": ["normalised line", "..."] }
            ]
          }
        ]
      }
    ]
  }
  ```

  The location key of an entry is its `path` and its `code` lines, joined. No title is part of it, and the key is derived with `locationKey(path, code)` and never stored, so a stored key cannot drift from the code beside it. `startLine` and `endLine` are where the code stood at that rejection's `recordedHead` and are for the reader. The comparison never uses them. `code` holds the normalised lines, not a hash, because finding moved code needs the lines themselves. Guards are stored as lines for the same reason. The title and reason are the only free text. There is no timestamp, so a record is a pure function of its inputs and the repository. `guards` holds the code outside the cited range that the disproof rests on, such as a check in the caller that rejects the input, and is empty when the claim was disproved by the cited code alone. A rejection holds at most 3 guards, each a path and its normalised lines, and they are part of the rejection and never of the entry's location key, so two rejections at one place can rest on different guards. The `path` is a repository relative path with forward slashes, with no leading `./`, no `..` part, and not absolute, and the schema refuses one that is not. An unknown key, a version other than 1, invalid JSON, an empty `code`, an empty `rejections`, an empty guard `code`, more than 3 guards in a rejection, or more than 5 rejections in an entry fails the schema. A title is at most 200 characters and a reason at most 600, so the file and the packet stay small.
- **Normalising code:** each line is trimmed, every run of whitespace inside it becomes one space, and blank lines are dropped. Comments are not stripped, so a comment edit counts as a change. A re-indent or trailing whitespace does not. Anything cleverer, such as parsing the language, would make the rule different per language and is rejected.
- **Finding the cited code at a head:** `git show <head>:<path>` through `Bun.spawnSync`, the way `review-scope.ts` runs `git`, with `core.quotepath=false`. Only a path read from the memory file is ever passed to `git`, never a path from a candidate, and the schema has already refused an unsafe one. The file is normalised line by line while the original line number of each kept line is remembered. The entry's `code` is searched as a contiguous run of kept lines, and every match gives a range from the original line of its first kept line to the original line of its last. A `git show` that fails because the path is not in the tree is "gone", which counts as changed. A guard is looked for the same way, as a contiguous run of normalised lines anywhere in its own file, since a guard has no anchor: it only has to still exist. A guard path read from the memory file is passed to `git` only after the schema has refused an unsafe one. A head that is not a commit is checked once, up front, with `git cat-file -e <head>^{commit}`, and is an error, so a bad SHA is never mistaken for a deleted file.
- **What `filter` reports:** a candidate gets `prior-rejection-at-location` when it has a cited `line`, its path equals an entry's path, and at least one match range of that entry's code contains the candidate's `line`, or overlaps `line` to `endLine` when that is given. The candidate's own anchor is what handles two things plain content search cannot: the same lines appearing twice in a file, and a lens citing a place that is not the one that was disproved. It errs towards `fresh`: a lens that anchors just outside the remembered range gets a fresh judgement, which is today's behaviour. A candidate can match several entries with overlapping ranges, and then every rejection of every matching entry is reported, newest first. No other rule reports a prior rejection. Every other candidate is `fresh` with a cause:
  - `cited-code-changed`: an entry exists for the candidate's path, but none of its code is found at the head around the candidate's anchor, because a line changed in content, a line is gone, or the file is gone
  - `no-record`: no entry has the candidate's path, or the candidate's path is not a safe relative path
  - `no-line`: the candidate cites no line, such as a whole-file observation, whatever the memory holds

  - `guard-changed`: the cited code is unchanged and found at the candidate's anchor, but every rejection there stored a guard that is no longer present at the head, so the reason it rested on is gone
  - `memory-over-budget`: rejections apply, but none fits the output budget described below

  A rejection applies only when every one of its guards is present at the head. A rejection whose guard is missing is not reported and is never carried as context, so a guard removed outside the cited range returns the claim to a fresh judgement. This closes the case of a disproof resting on code the range did not cover, at the cost that a guard that moved into another file counts as removed, which is the safe direction. A guard whose text was copied to another place in its file while the original was removed still counts as present, which is accepted and noted in the risks.

  The cause is for the reader and the tests. The adjudicator treats every `fresh` candidate the same way. Changed code never carries a remembered reason forward, so a changed location can never be judged from the old reasoning. A candidate with no line is not refused and does not stop the review, because `mr-review` already handles whole-file findings.
- **Filter input and output:** `candidates.json` is `{ "candidates": [{ "id", "path", "line"?, "endLine"? }] }`, ids unique and non-empty, `path` a non-empty string, `line` and `endLine` positive integers when present, and `endLine` not before `line`. A candidate carries no title, because none is needed to find a location. The output is one JSON document with a result for every candidate in input order, and then a `rejections` section, last, that holds the remembered text:

  ```json
  {
    "head": "<40 hex>",
    "results": [
      { "id": "c1", "path": "src/parse.ts", "line": 12, "status": "prior-rejection-at-location" },
      { "id": "c2", "path": "src/parse.ts", "line": 40, "status": "fresh", "cause": "cited-code-changed" },
      { "id": "c3", "path": "src/other.ts", "status": "fresh", "cause": "no-line" }
    ],
    "rejections": [
      {
        "id": "c1",
        "omitted": 0,
        "items": [
          { "ref": "<12 hex>", "title": "Parse crashes on empty input", "reason": "...", "recordedHead": "<40 hex>", "startLine": 10, "endLine": 14 }
        ]
      }
    ]
  }
  ```

  `ref` is `rejectionRef(locationKey, title)`, twelve hex characters derived from the entry's location key and the rejection's title. Both are unique together within a memory, because an entry holds one rejection per title and an entry is identified by its location key. A `ref` is how a later step names one remembered rejection, so a position that shifts when a list is cut never names the wrong one. Only candidates with a `prior-rejection-at-location` result appear in `rejections`. The script exits 0 whenever it could read its input and the memory, so a prior rejection is a normal result. `filter` never writes.

  **The output is bounded.** `review-packet.ts` keeps only the last `EVIDENCE_TAIL_CHARS` (6000) characters of each evidence file, and the first characters of a longer file are cut. A rejection is up to 800 characters of title and reason, and a location can hold 5, so an unbounded `rejections` section would lose its earliest rejections, the very text the adjudicator compares against. So `rejections` goes last and the script measures the text it prints: `REJECTIONS_BUDGET_CHARS` is defined as `EVIDENCE_TAIL_CHARS` imported from `review-packet.ts`, less 1000 characters kept for the end of the document. Candidates are taken in input order and each one's rejections newest first, and a rejection is listed only if the section would still fit the budget. One that does not fit is left out whole, never cut, and counted in that candidate's `omitted`. A candidate with none that fits is reported `fresh` with the cause `memory-over-budget`. This is the same direction as every other limit in the design: loss of a remembered rejection costs a fresh judgement, never a hidden finding. A test derives the budget from the exported constant, so a change to the packet limit moves it. The importing does not change `review-packet.ts`.
- **Record input and rule:** `outcome.json` is the adjudicator's whole account of one review, with every list optional and empty by default.

  ```json
  {
    "disproved": [{ "title", "path", "line", "startLine", "endLine", "reason", "guards": [{ "path", "startLine", "endLine" }] }],
    "reversed": [{ "id", "rejection" }],
    "droppedAsPreviouslyDisproved": [{ "id", "rejection" }]
  }
  ```

  - `disproved`: a candidate found false by fresh judgement. `line` is the line the candidate cited, and `startLine` to `endLine` is the range the adjudicator read to disprove it. The script refuses a `line` that is not inside that range, so the range-includes-anchor rule is checked on input and not left to the adjudicator's care. It also refuses a range over 80 lines, a path or range that does not exist at the head, an empty or over-long title or reason, and an unsafe path. It reads the lines at the head, normalises them, and adds a rejection to the entry with the same location key, creating the entry when there is none. A rejection with exactly the same title text as one already in that entry replaces it. When an entry would then hold more than 5, the oldest is dropped. Two disproved candidates at one location in one outcome are both stored.
  - `guards`: optional, at most 3. Each is another place the disproof rests on, a path and a range of at most 80 lines read at the head under the same rules as the cited range, and the script stores their normalised lines with that rejection. The adjudicator uses guards for what it relied on outside the cited range: the check in a caller, the constant, the validation upstream. Without guards, a rejection that rested on code outside the range kept applying after that code was removed, and a real regression went unreported. With guards, the same removal returns the claim to a fresh judgement.
  - `reversed`: the adjudicator raised a finding that is the same claim as a remembered rejection. It names the candidate by `id` and the rejection by `rejection`, the `ref` printed for it in `memory-filter.json`. The script refuses an id that is not a `prior-rejection-at-location` result there, a `ref` that is not listed for that id, or a missing file, as it does for `droppedAsPreviouslyDisproved`. It removes that rejection and nothing else from the memory as it stands now, and removes the entry too when it holds no more. A `ref` no longer in the memory changes nothing. A finding that is a different claim from every listed rejection reverses nothing, so an unrelated rejection at the same place is never lost. The earlier design identified a reversal by path and line and deleted every rejection at the place, which was unsafe the other way: it forgot true rejections of unrelated claims.
  - `droppedAsPreviouslyDisproved`: a candidate the adjudicator dropped as the same claim as a remembered one, named by `id` and by `rejection`, the `ref` of the listed rejection. The script reads `.review/mr-<iid>/<head-sha>/memory-filter.json` and refuses an id that is not a `prior-rejection-at-location` result there, a `ref` not listed for that id, or a missing file. The same id and `ref` cannot be both reversed and dropped. Nothing is stored for these, because the remembered rejection is already stored.

  **Refusal.** Every item is checked before any write, and all problems are collected, not just the first. A refused outcome exits 3 and prints one plain message per refused item, naming the list in plain words ("disproved candidate 2", "dropped candidate 1") with its position and the problem, and no raw field names. Nothing is written. An unusable argument, an unusable repository, a bad head, or an unreadable memory or filter file exits 1. The memory file is written to a temporary file in the same directory and renamed over the memory file, so a failed record never leaves half a file, and when nothing changes and no file exists none is created. Because the cited range must include the cited line, a rejection can only be stored for code the candidate really pointed at.
- **Record output:** the command prints `{ "recorded": <n>, "reversed": <n>, "previouslyDisproved": "<markdown>" }`. `previouslyDisproved` is the markdown list for the output section, one bullet for each `droppedAsPreviouslyDisproved` item: the candidate's path and line from the filter result, the remembered title, the earlier reason, and the first 12 characters of the head it was disproved at, all read from the listed rejection with that `ref`, in the form ``- `src/parse.ts:12` Parse crashes on empty input. Earlier reason: <reason> (judged at <12 hex>)``. It is the empty string when nothing was dropped that way. The title and reason are run through `sanitizeHumanText` from `human-text.ts`, which does one thing: it replaces an em or en dash with a spaced hyphen. It does not clean a path, a home directory, or internal field names. Keeping those out of the reason is the adjudicator's job, stated in the recording rule, and the test for the list asserts the dash rule and nothing wider, so the scenario describes what the sanitiser really does.
- **What the adjudicator records:** only a candidate found false for the code at the pinned head by fresh judgement. That means the adjudication steps that read the code, run a reproduction, or find a guard, and the step that drops a claim whose trigger cannot occur. Duplicates, claims dropped as already raised in the discussions, downgrades that are still raised, claims that rest only on a name or comment, style preferences, and candidates dropped as previously disproved are not recorded. Alternatives: record every drop, which would remember a claim that was merely unproven and turn a missing piece of evidence into a settled argument; record nothing from step 7, which loses the common "cannot be triggered" rejection. The rule records what adjudication can state as false and leaves the rest to be judged again, which costs a re-read and never a lost finding. The reason is written in plain language with repository relative paths only, as the human-facing output rule asks, since it may be printed back to the operator. The adjudicator also names, as guards, each place outside the range it read that the disproof rests on, up to 3. A claim whose disproof rests on more than that, or on something no file's lines show, such as runtime configuration, stored data, or an outside service, is not recorded: it is judged again in a later review, which costs a re-read and never a lost finding. Alternative considered: widen the cited range past 80 lines to cover the guard, which would make every unrelated edit nearby invalidate the rejection and would not reach a guard in another file.
- **Where the skill calls it:** in `skills/code-review-max/SKILL.md`, at the start of "Adjudicate every candidate".
  1. After the lenses return, the skill gives every candidate an id `c1`, `c2` and so on in the order the lenses returned them, and writes the id at the head of each candidate in the lens evidence files, so a reader can match a candidate to a filter result. It writes each id, cited path, and cited line, when there is one, to `.review/mr-<iid>/<full-head-sha>/memory-candidates.json`, runs the filter invocation, and persists its output beside it at `memory-filter.json`. A non-zero exit stops the review. When no lens returned a candidate, the filter step is skipped.
  2. `lens-candidates.json` keeps every candidate, now as `{"candidates":[{"id":"c1","severity":"Low"}, ...]}`. `review-fanout.ts adjudication` reads only `severity`, so the extra key changes nothing there, and the mode is chosen from all candidates exactly as before. The skill does not remove a candidate on the filter's say.
  3. The adjudication packet gets `memory-filter.json` as one more `--evidence` file, placed last, so the adjudicator reads the remembered rejections in the packet it already opens first. The packet keeps only the last 6000 characters of an evidence file, which is why the file goes last, why its `rejections` section is the last part of it, and why that section is held to a budget below that limit. Whatever the memory holds, the whole section reaches the adjudicator, and only the compact `results` before it can be cut.
  4. A new step 0 in the adjudication list, before reading any cited code: for a candidate the filter marked `prior-rejection-at-location`, compare its claim with each remembered rejection listed for it, using the bad behaviour and trigger the candidate states, not its wording. If it describes the same bad behaviour under the same trigger, drop it without re-investigating, do not record it, and name it under `droppedAsPreviouslyDisproved`. Otherwise judge it fresh by the numbered steps, however close the wording. When unsure whether it is the same claim, judge it fresh: a repeated look costs today's behaviour, a wrongly dropped claim costs a finding. A `fresh` candidate goes straight to the numbered steps.
  5. If the adjudicator raises a finding that is the same claim as a remembered rejection listed for a candidate, judged by behaviour and trigger, it names that candidate and that rejection's `ref` under `reversed`. A finding that is a different claim reverses nothing.
  6. After the numbered steps the adjudicator writes `.review/mr-<iid>/<full-head-sha>/memory-outcome.json` with `disproved`, `reversed` and `droppedAsPreviouslyDisproved` under the recording rule above, and the skill runs the record invocation. When no candidates exist, the record step is skipped. An exit of 1 stops the review. An exit of 3 does not: the message names every refused item, so the main conversation corrects each from the code and the filter result and runs `record` again. Items still refused after that are removed, and `record` runs once more. A removed `disproved` or `reversed` item is not remembered, which costs a fresh judgement in a later review. A removed `droppedAsPreviouslyDisproved` item revokes the drop: the candidate is judged by the numbered steps, and a finding from it goes into the output as any other. The output then says under Verification, in plain words, how many items were not remembered. `max.md` is written after the last `record` run, so a refused outcome delays no finding and changes none. A standard-mode reply whose `outcome` is refused is not corrected from prose and goes to `main` mode as before, and in `main` mode this recovery applies.
  7. In a `delta` review the skill gives the lenses the earlier review without its `### Previously disproved` section, written to `.review/mr-<iid>/<full-head-sha>/earlier-review.md`, and not `max.md`, and adds to the brief that the earlier review holds findings only and nothing in it but a finding is to be confirmed, carried, or reported. The earlier review's section is in `path:line` form, which a lens told to report any unfixed earlier finding would otherwise read as one. `### Earlier findings` names findings only, and the earlier dropped list is not copied into the later review's: the later list holds only what the later review dropped. `review-scope.ts` still reads the earlier `max.md`, whole, for the verdict. A `full` review hands the lenses no earlier review.
  8. The output template gains `### Previously disproved` between Findings and Verification, filled with `previouslyDisproved` as printed by `record`, and left out when it is empty.

  This runs the same in a full and a delta review, because the filter reads only candidates, memory, and the head. Delta review's own sentence about earlier findings is unchanged. The new section sits among headings `review-scope.ts` does not read: `readVerdict` takes the `**Verdict:**` line and the final marker only.
- **What the standard-mode subagent returns:** in `standard` mode a fresh read-only subagent adjudicates, and the main conversation, not the subagent, writes `memory-outcome.json` and runs `record`. The subagent gets the packet, the Severity rules, step 0, the recording rule, and the shape of the outcome. Its reply ends with one fenced JSON object `{ "findings": "<markdown>", "outcome": { ... } }`: `findings` is the numbered findings in the output format, empty when there are none, and `outcome` is the same object `record` reads. The main conversation writes `outcome` unchanged to `memory-outcome.json`. A reply with no such object, or whose `outcome` fails `record`, does not get recorded from prose: the main conversation adjudicates in `main` mode instead. The same contract in `main` mode is just the conversation producing the same two things itself, so `record` has one input shape however the review was adjudicated.
- **Every candidate dropped as previously disproved:** a review whose candidates were all dropped by step 0 has no findings. The mode, chosen from severities, was `standard` or `main`, not `none`, because the candidates exist. The skill writes `No findings.` and a `PASS` verdict, followed by the `### Previously disproved` list from `record`, so the operator sees that candidates were dropped and why. The `none` mode keeps its meaning, no lens returned a candidate, and there the filter and record steps are skipped, no list exists, and nothing is hidden. The skill states both cases in the output rules.
- **How `mr-review` treats the section:** one rule in Phase 5 of `skills/mr-review/SKILL.md`. The `### Previously disproved` list in the accepted `max.md` is context and is not a finding: it is not carried into the consolidated list, is not posted, and is not counted. `mr-review` prints it in the conversation with its drafts, so the operator sees what was dropped before publishing, and leaves it out of `summary.md` and every note. If `mr-review` disagrees with a listed rejection after reading the code itself, it raises that claim as its own finding with its own evidence. It does not restore a dropped claim on the strength of the list alone.
- **Failures:** an invalid iid or head, an unusable repository, an unreadable or invalid memory file or filter file, and a bad head exit 1 with one plain message on standard error and no write. A malformed or refused outcome file exits 3 with a message per refused item, as described under the record rule, and no write, so the one failure a model can correct has its own code. A missing memory file is not a failure. A corrupt memory is refused, not repaired, and the message names the file and says that deleting it forgets the remembered rejections. Failing closed matches the other review scripts, where a non-zero exit stops the stage; the alternative, ignoring a corrupt file, would hide a lost memory and rewrite it. A candidate with no line, an unsafe candidate path, a path with no entry, or rejections left out for the budget is not a failure.
- **Other documents:** `skills/delivery/workflows/mr-review-to-ready.md` gets a short paragraph beside the existing delta-scope paragraph saying that a later review does not re-investigate a rejection while its cited code is unchanged and the claim is the same, that the dropped list is in the output, and the limits. `docs/workflow.md` gets one row-level sentence in the review loop. `docs/reference.md` gets a "Review memory" section after "Review scope" with both invocations, the file, the rule in two sentences, and the limits. The skill markdown must not name a forge, tracker, or host product, by the generic boundary in `CONTRIBUTING.md`.
- **Existing files touched:** `skills/code-review-max/SKILL.md`, `skills/mr-review/SKILL.md`, `skills/delivery/workflows/mr-review-to-ready.md`, `docs/workflow.md`, `docs/reference.md`, `factory/scripts/workflow-contracts.test.ts`, and `skills/delivery/checks/delivery-specs.test.ts`. **New files:** `factory/scripts/review-memory.ts` and `factory/scripts/review-memory.test.ts`. Neither `review-scope.ts`, `review-rounds.ts`, `review-fanout.ts`, nor `review-packet.ts` changes.

## Test seam

- Primary: `factory/scripts/review-memory.test.ts` builds a real temporary git repository in each test, with `git init`, a configured identity, and commits of small TypeScript files, so heads are real SHAs and `git show` is the real reader. It runs `review-memory.ts` as a command with `Bun.spawnSync`, the way the other script tests do, and asserts the exit code, the standard output JSON, the standard error text, and the bytes of `.review/mr-<iid>/rejected.json` before and after. The same file calls `normaliseCode`, `locateCode`, and `locationKey` directly for the whitespace forms and the duplicate-range case, and derives the budget it asserts from `EVIDENCE_TAIL_CHARS` and `REJECTIONS_BUDGET_CHARS` and from `buildReviewPacket`'s own tail, so the whole `rejections` section is shown to survive the packet's cut. It covers every scenario in the `review-memory` spec that concerns the script: store with reason and cited code, pinned head over working tree, second rejection at one location, atomic refusal of a bad record, anchor outside the range, oversize range, empty reason, unknown head, prior rejection on unchanged code, moved code, whitespace edit, delta scope, duplicate code in two places, a removed guard, a moved guard, an output over budget, changed line, removed line, deleted file, renamed file, no cited line, a reversed rejection removed alone, a reversal of a rejection already gone, every refused item named at once, a corrected and a trimmed outcome, another merge request, never rejected, no file, corrupt and unknown-version file, bad id and head, dropped candidate in the list, the dash rule, a bad dropped reference, and no list when nothing was dropped.

## Risks / Trade-offs

- The adjudicator judges a different claim to be the same and drops a real finding → the rule says to judge fresh when unsure, only candidates at a location whose cited code is unchanged can be dropped, every drop is listed with its earlier reason, and deleting `rejected.json` forgets everything. This is the main residual risk, and it moved from a script's string match to a reader's comparison on purpose, since the string match would have rarely matched at all
- A wrong earlier rejection is kept while its cited code stays the same → the dropped list is in every output where it applies, the memory is only for the same merge request, and `reversed` forgets exactly the rejection the adjudicator contradicts and no other at that place
- A claim whose cited code is unchanged can still be made true by a change elsewhere, such as a removed guard above it or in another file → the adjudicator names each such place as a guard, the rejection is reported only while every guard is still present, and a claim resting on more than 3 places or on something no file shows is not recorded. A guard whose text is copied elsewhere in its file while the original is removed still counts as present, and an unrecorded or misnamed guard is the adjudicator's miss, which the dropped list lets the operator see
- Code that is changed and then restored brings an old rejection back, even when a finding was raised at the changed text in between → the adjudicator reads the remembered head and reason beside the candidate and may judge fresh, and `reversed` removes only the rejection it names. Accepted: the rejection was true for that text
- A cited range that moves into a block that was copied and then deleted at the original place → the candidate's anchor line must lie in a match, so a copy elsewhere does not attach a reason to the original
- Stale entries whose code is gone stay in the file, unread → bounded by the number of rejections in one merge request's reviews, and deleting the file clears them
- The memory is lost on a fresh clone or another runtime, because `.review/` is worktree-local → documented in the skill, the workflow, and the reference rather than hidden. Delta review has the same limit
- A refused outcome stopping a finished adjudication → exit 3 names every refused item, the conversation corrects it once, then removes what is still refused and goes on, so only an unusable repository or file, which no retry fixes, stops the review. The cost of a removed item is that it is not remembered or that its drop is judged fresh
- Delta lenses reading the dropped list as unfixed findings → the lenses get the earlier review without that section and a brief that says nothing but findings is to be reported
- A corrupt memory file stops the review → the message says what to delete, and silently ignoring it would hide a lost memory
- A second reversal of a rejection that is already gone is a no-op, and a reversal names a rejection by a reference derived from its place and title, so a changed list cannot make it hit another one
- Two reviews of the same merge request at once could overwrite each other's record → accepted: review runs inline in one conversation, and the rename keeps either file whole
- Pack docs and the contract tests match exact strings, so a markdown edit that drifts breaks them → the contract assertions are derived from the script's exports and move with them
