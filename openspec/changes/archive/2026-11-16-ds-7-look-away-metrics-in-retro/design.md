## Context

Retro looks back over a run and proposes changes to the environment the work ran in. It reports nothing about how much supervision the run needed. The operator therefore picks `MAX_PARALLEL_WORKTREES` and how closely to watch by feel.

Two records already hold the evidence, and both are in the state root (`.delivery/runs/` unless `DELIVERY_STATE_ROOT` is set):

- The worker journals, `<state-root>/workers/<run-id>/<key>.md`, one per key in an auto fan-out. Each worker writes its own stops, approvals, and decisions there through `ledger-store.ts`, so the journal has the same section layout as the ledger. The coordinator is the only writer of the run ledger and "worker prose is never merged into the ledger" (`delivery-ledger.md`), so a fan-out run's worker stops live only in the journals.
- The run ledger, `<state-root>/<run-id>.md`, whose Stops and Approvals sections hold one line per operator interruption. Since DS-6 every new line begins `- <yyyy-mm-ddThh:mm:ssZ> `. Older lines begin `- <yyyy-mm-dd> `. `ledger-store.ts` already owns how those sections are found and what a timed line is (`isLedgerTime`, `LEDGER_TIME_FORMAT`, and the private `sectionEntries` and `TIMED_BULLET`).
- The worker dispatch records, `<state-root>/workers/<run-id>/dispatch.json`, which auto's fan-out writes with one entry per worker: `key`, `dispatchedAt`, and an optional `finishedAt` that the coordinator sets when it reconciles or stops the worker. `worker-watch.ts` owns the `WorkerDispatch` schema and `liveWorkers`, and the wave selector in `config.ts` already treats a worker with no `finishedAt` as running and counts it against the limit.

Findings from reading the repository:

- Real Stops lines do not all look like the format page's template. The live ledger in this repository has `- 2026-11-09 run groom - groom done; …`, `- 2026-11-09T13:02:00Z run auto - …`, and `- 2026-11-09T13:40:12Z DS-1 draft - …`. They use a plain hyphen after the stage, not the em dash, and the key is sometimes the word `run`. A parser that waits for an em dash would drop every real line, so the stage is read from the position after the key and the separator is not matched.
- `dispatch.json` is state, not source: it is gitignored with the rest of the state root, and only the auto fan-out writes it. A one-ticket run that never fanned out has none.
- `loadConfig()` reads only the environment, so reading the current limit from it adds no file read.
- `retro.md` has ten numbered steps, and Present is the last. Nothing else refers to step numbers inside retro.

## Goals / Non-Goals

**Goals:**

- Three measured numbers and a raise-or-hold suggestion, computed the same way every time by one script, shown by retro in plain words
- Every number says when it cannot be known: unknown, at least N, or an unreadable line listed by name. No figure is guessed
- Reuse the writer's definition of the Stops and Approvals sections and of a timed line, and the dispatch schema, so none of the three can drift from the thing that writes or validates the record
- A suggestion that is advice only: nothing in the script or the workflow has a path to a setting

**Non-Goals:**

- Applying the suggestion, or any setting change
- Reading the tracker, the forge, or a clock. Worker journals are read, but only for stops and approvals, never for the peak
- Adding times to the ledger, backfilling older lines, or estimating from them
- Measuring from run start or run end
- Writing the metrics into the ledger

## Decisions

- **One script, pure calculations plus a thin command line.** `factory/scripts/look-away-metrics.ts` exports four pure functions and one command line. It follows the shape of `worker-watch.ts`: an exported command string, exported functions that take already-read inputs, and an `import.meta.main` block that reads files, prints, and sets the exit code.
  - `peakConcurrency(dispatch: unknown | undefined)` returns the peak or why it is unknown
  - `stopsByStage(sources: string[])` takes the ledger text and each journal's text and returns the stop counts
  - `longestStretch(sources: string[])` takes the same texts and returns the longest stretch or why it is unknown
  - `idleWorkers(ledger: string)` returns the keys the coordinator stopped for being idle, read from Decisions
  - `runLimit(ledger: string)` returns the limit the run used, or unknown
  - `suggest(peak, stretch, limits, idleWorkers, journalsComplete)` returns raise or hold, the limits, and the reasons
  - `lookAwayReport({ ledger, journals, dispatch, configuredLimit })` composes them
  - Alternative: have the retro model count lines. Rejected, because a count or a gap taken by a model is the thing the ticket exists to replace, and a deterministic script can be tested on fixtures.
- **Command and arguments:** exported as `LOOK_AWAY_INVOCATION`, the string `scripts/look-away-metrics.ts <state-root> <run-id>`, written as one double-quoted literal with the same `biome-ignore format` line the other invocation constants carry, so a test can read it out of the source. The script reads `<state-root>/<run-id>.md` and `<state-root>/workers/<run-id>/dispatch.json`, the same two paths the delivery workflows already use. The run id is the ledger file's name without `.md`, which `delivery-ledger.md` defines. It reads `<state-root>/workers/<run-id>/*.md` as the journals (a missing folder is a run that never fanned out). It prints one JSON object with two-space indentation and exits 0. Exit 1 is a plain failure (no ledger, invalid configuration) with the message on standard error and nothing on standard output. Exit 2 is a usage mistake.
- **Report shape.** Fixed here so the tests and the retro wording agree:

  ```json
  {
    "peak": { "state": "exact" | "at-least" | "unknown", "workers": 3, "reason": "…" },
    "stops": { "total": 4, "byStage": { "execute": 2, "draft": 1 }, "unreadable": ["- … full line"] },
    "journals": { "read": 2, "unreadable": ["DS-3.md"] },
    "idleWorkers": ["DS-2"],
    "longestStretch": { "state": "known" | "unknown", "seconds": 18900, "text": "5h 15m", "from": "<time>", "to": "<time>", "includesWaiting": true, "reason": "…" },
    "suggestion": { "action": "raise" | "hold", "runLimit": { "state": "known" | "unknown", "value": 4 }, "configuredLimit": 4, "reasons": ["…"] }
  }
  ```

  `workers` is present only when the state is `exact` or `at-least`; `reason` only when `unknown`; `seconds`, `text`, `from`, `to`, and `includesWaiting` only when `known`; `value` only when the run limit is `known`. Journals are listed in sorted file-name order, so the bytes do not depend on directory order. `byStage` keys are lower case and are written in sorted order, so the bytes do not depend on file order. `unreadable` keeps file order. `text` is `<hours>h <minutes>m` with the minutes rounded down and no padding; `seconds` is the exact length that the suggestion compares.
- **Peak concurrency: a sweep over start and end events.** Each worker with a `finishedAt` after its `dispatchedAt` contributes a start event and an end event. A worker with no `finishedAt` contributes a start event and no end event, so it runs to the end of the record. At the same instant ends sort before starts, so a worker that finishes as another is dispatched does not overlap it. The peak is the largest running count, at least 1 for any non-empty record. A `finishedAt` equal to `dispatchedAt` occupies no time and adds no events, so only the floor of 1 counts it. A `finishedAt` earlier than `dispatchedAt` makes the whole peak unknown, with the reason, because no honest reading exists. The state is `at-least` when any worker has no `finishedAt`, and `exact` otherwise. A duplicate key fails the schema (`each key is watched once`), so a worker dispatched again in a later turn makes the peak unknown, with the reason that a key appears twice. The script does not try to repair it, because a coordinator overwriting the first entry is invisible here, and an understated peak can only make the suggestion hold. Cost is O(w log w) for w workers, and w is bounded by a run's keys. The records are validated with `WorkerDispatch.safeParse` from `worker-watch.ts`, so the shape has one definition. Missing file, unparseable JSON, and a schema failure each give `unknown` with a plain reason, and none stops the other parts.
  - Why a lower bound for the unfinished case: the figure must agree with what the wave selector saw, and it saw those workers as live. The label says the figure was not confirmed by finish times. At retro time a missing `finishedAt` usually means the coordinator never recorded it, so the lower bound can be higher than the real overlap. It is therefore shown to the operator but never used to raise (see "The suggestion is code").
  - Alternative: infer a worker's end from its journal's last write. Rejected: it estimates.
- **Journals are read for stops and approvals, and a failure is loud.** The first draft excluded journals for fear of double counting, but nothing is duplicated: the coordinator never copies a worker's stops or approvals into the ledger, so in an auto fan-out (the runs where peak concurrency matters) a ledger-only reading undercounts stops and overstates the stretch, which pushes the suggestion toward raise. The script reads every `*.md` under `workers/<run-id>/` with the same section readers, counts their Stops lines with the ledger's, and merges their timed Stops and Approvals lines into the interrupts. A journal that exists but cannot be read is named in the report and makes the stretch unknown and the suggestion hold, because a missing record could hide an interrupt. Lines identical to a ledger line are not collapsed: a copy would only repeat an interrupt (no effect on the stretch) and nothing in the record shows copying. A missing `workers/<run-id>` folder is a run that never fanned out and is normal.
- **Stops by stage: one line, one stop, and a surfaced remainder.** The Stops section is read through the writer's own reader. A line is parsed as `- ` then a time or a date, then a key (a work-item key, or `run`), then a stage word. The separator is not matched. Stages are lower-cased and counted in a map. The coordinator's stop of an idle worker is not a Stops line. It is the Decisions line `worker <KEY> idle for <N> minutes; stopped`, an automatic stop and not an operator stop, so it is not counted as a stop or an interrupt. It is read separately (`idleWorkers`), named in the report, and it holds the suggestion, since a run that had to lose a worker to inactivity is not evidence that more concurrency is safe. A line that does not parse is not dropped: it is kept in `unreadable`, counted in `total`, and counted under no stage, so `total` always equals the stage counts plus the unreadable lines. This is the stated risk of free-text stops. Approvals are not stops.
- **Interrupts and the longest stretch.** An interrupt is a Stops or Approvals line that `ledgerLineTime` says is timed. Times are sorted as instants, across both sections together, because a stop and an approval from the same hour sit in different sections of the file. The stretch is the largest difference between consecutive instants. The report keeps the two bounding times and the exact seconds. Fewer than two timed lines is `unknown`.
  - **The stretch includes waiting.** It is wall-clock time between two timed lines, so it includes time the run sat in a waiting status for a person, overnight waits during review quiet hours, and operator decisions recorded only in Decisions (which have no fixed shape and no time guarantee). None of these is timed in the ledger, so none can be subtracted without estimating. The report says the stretch includes waiting (`includesWaiting`), the retro step says so in words, and every raise reason repeats it, so the operator reads a raise as a prompt to look, not as proof of unsupervised work. Not splitting on Decisions lines is deliberate: guessing which Decisions lines were operator choices would be reading prose.
  - **Untimed lines can hide a gap, and the rule is conservative.** An untimed Stops or Approvals line still was an interruption, at an unknown moment. Ignoring it would let a long gap that it split be reported as unbroken, which would push the operator toward a wrong raise. Rule: an untimed line with a readable `yyyy-mm-dd` date can fall anywhere in that UTC day, so a gap is left out when that day overlaps the open interval of the gap. An untimed line with no readable date can fall anywhere, so it leaves out every gap. The longest stretch is the longest of the gaps that remain, or unknown when none remain. Nothing is ever estimated: a left-out gap is simply not claimed. Alternative: ignore untimed lines. Rejected because it overstates. Alternative: make any ledger with an untimed line unknown. Rejected because every ledger that spans the DS-6 change would be permanently unknown, even when the old lines are weeks away from a measurable gap.
  - Run start and run end are never used: `Created:` is a date, and the end has no time.
  - Cost is O(n log n + n·m) for n timed and m untimed lines, which is small for a ledger.
- **Reusing the writer's readers: two exports and no behaviour change.** `ledger-store.ts` gains `ledgerEntryLines(markdown, section: "Stops" | "Approvals" | "Decisions"): string[]`, a wrapper over the existing `sectionEntries` that finds the heading as the writer does, and `ledgerLineTime(line): string | undefined`, which returns the time when the trimmed line is `- <time>` followed by a space or the end of the line and `isLedgerTime` accepts the time. `ledgerEntryProblems` is changed to call `ledgerLineTime` in place of its inline check, so the check the writer enforces and the check the metrics use are one function. Existing `ledger-store.test.ts` cases stay as they are and must stay green. This is not a requirement change to `delivery-ledger-writes`. Alternative: copy the regexes into the new script. Rejected: two copies drift, and this very change depends on DS-6's definition being the only one.
- **The suggestion is code, and it fails closed.** `suggest` returns raise only when all of these hold: the peak state is `exact` with a worker count at least the limit the run used; the limit the run used is known and equals the limit configured now; the stretch is `known` with `seconds >= 14400`; no journal was unreadable; and no worker was stopped for being idle. Everything else is hold. Every hold names each failed condition in `reasons`, and raise names the conditions that held and that the stretch counts waiting. An `at-least` peak is never enough: it is an upper estimate that may come from a worker the coordinator never marked finished, and raising on missing data would fail open. A peak above the limit (the limit was lowered mid-run) is reached when exact. The four-hour threshold is one constant in the script, named for what it is, and the retro text states it in words. The reasons are written in the plain words retro shows, with no field names. Alternative: leave the judgement to the retro text. Rejected: a threshold in prose cannot be tested, and the model could apply it differently on different days.
- **Limit and read-only guarantee.** There are two limits. The limit the run used is read from the ledger's Decisions section: auto records `level <level>: maxParallelWorktrees=<n> maxFixAttempts=<n> maxReviewRounds=<n>` at its start, which holds the run's effective values with any `MAX_PARALLEL_WORKTREES` override applied. The run contract is not read: it freezes only the level word, so it cannot give an overridden value. Reading the limit from the retro shell would be wrong because the shell's `DELIVERY_LEVEL` is not the run's (a `max` run retro'd in a default shell would see 4 against its real 8 and be told to raise). A line whose value is not a positive whole number is ignored; with several usable lines the highest wins, because a higher limit is harder to reach; with none the limit the run used is unknown. The limit configured now is `loadConfig().maxParallelWorktrees`, so the level preset and the `MAX_PARALLEL_WORKTREES` override both apply, and a malformed value fails closed as everywhere else. It is shown for context, and raise requires it to equal the limit the run used: advice to raise from a number the operator no longer has would mislead. The script imports only read functions (`readFileSync`, `existsSync`) and no function that writes, creates, moves, or removes a file. A test reads the source for that. A second test runs the command on a state root and checks that no file changed. Together they are the "no write path to settings" guarantee: a source check alone would miss a spawned writer, and a before and after check alone would miss a path no fixture exercises.
- **Retro step.** `retro.md` gains `### 10. Measure look-away`, and Present becomes step 11. The step runs `bun "${FACTORY_ROOT}/scripts/look-away-metrics.ts" <state-root> <run-id>` with the state root and run id taken from the ledger found in Preconditions, so no new lookup is invented. It says the figures cover the whole run, and that a one-ticket retro shows the same figures and says so. It lists the plain-word presentation for each number and its non-numeric outcomes (unknown, at least N, unreadable lines, unreadable journals), says the longest stretch includes time spent waiting, names any worker stopped for being idle, and presents the suggestion with the limit the run used, the limit configured now, and the reason. It says the suggestion is advice: retro changes no setting, creates no work item for it, and adds no checkpoint in either mode. It says that when the script fails, retro reports the figures as not measured with the script's message, estimates nothing, and carries on. The Present step shows the measurement ahead of the proposals. The invocation in the page is checked against the exported constant, so it is not a second source. The step does not write to the ledger, so the Ledger writes section is unchanged.
- **Reference page.** The script's command is added to the "Cost-control scripts" list, copied from the exported constant by hand and covered by the same contract test as the workflow page (see the test seam).

## Test seam

- **Primary:** `factory/scripts/look-away-metrics.test.ts` calls the four pure functions on inline inputs for the boundary cases (equal instants, an exact four hours against 14399 seconds, the unfinished worker, the zero-length worker, an at-least peak against the limit) and runs the command line as a subprocess against temporary state roots for the report as a whole, the exit codes, the configured limit, and determinism. The command-line cases build their inputs from `factory/scripts/fixtures/look-away-ledger.md` (new), `look-away-dispatch.json` (new), and `look-away-journal.md` (new), which between them hold concurrent, back-to-back, unfinished, and several-wave workers, a duplicate key, timed and date-only stops and approvals in one ledger, stops that live only in a journal, a `level ...: maxParallelWorktrees=...` Decisions line, and an idle-worker Decisions line, and from the existing `ledger-date-only.md`. Subprocess tests use the shared subprocess budget from the root `bunfig.toml`, and a file run on its own states it with `setDefaultTimeout`, as the existing `ledger-store.test.ts` does.
- **Contract:** `skills/delivery/checks/delivery-specs.test.ts` gets a block named for the look-away step. It reads `LOOK_AWAY_INVOCATION` out of the script's source, the way the "durable ledger writer" block reads its constants, and asserts that `retro.md` contains it in a step that precedes Present, names the ledger as the source of the state root and run id, says whole run and single-ticket, names unknown, at least N, hours and minutes, raise, hold, the limit the run used and the limit configured now, and that the stretch includes waiting, says a failing script reports not measured and estimates nothing, and says it changes no setting. It asserts that the report's field names (`byStage`, `longestStretch`, `unreadable`) do not appear in the retro page, and that `docs/reference.md` carries the same command.
- **Writer exports:** `ledger-store.test.ts` adds direct cases for `ledgerLineTime` and `ledgerEntryLines` (heading variants, a second heading, a non-bullet line, text joined to the `Z`), and the existing writer cases stay unchanged and green.
- **What it catches:** a wrong overlap count, an end and a start at the same instant counted as overlapping, an unfinished worker presented as exact, a missing or broken dispatch record crashing the report, a stop dropped because it did not match a template, a date-only line estimated into a stretch, an untimed line that splits a gap being ignored, a stretch taken from one section only, a 3h 59m 59s gap rounded up into a raise, an `at-least` peak treated as unknown, as exact, or as enough to raise, a limit read from the retro shell instead of the run, journal-only stops undercounted, a stretch overstated for want of a journal line, a re-dispatched key crashing the report, any file changed by a run, the retro page drifting from the script's command or promising to apply the suggestion
- **What it misses:** whether the model running retro actually calls the script and presents its output faithfully. Only the wording can be pinned, as for every other retro step, and the script's failure is loud (a plain stderr message) rather than silent. Also whether the coordinator wrote `dispatch.json` as the auto workflow describes: only its schema is checked
- **Boundary that needs a fake:** none. The script is local and deterministic, so tests use real temporary files and the real configuration reader with `MAX_PARALLEL_WORKTREES` set in the spawned process's environment. No model, tracker, forge, or clock is involved, and the report depends on none of them
- **Held-out samples:** none are truly held out. `factory/scripts/fixtures/ledger-real-stops.md` (new) copies the Stops section of the live ledger `.delivery/runs/groom-2026-11-09-elephant-goldfish-checks.md`, three real lines with hyphen separators, the key `run`, and a blank line. The hyphen finding came from reading it, so it is a regression sample of real data, not a held-out one. The rule for the peak and the stretch is defined by the ticket and written from reasoning, not from sample data, so no sample can be held out for them

## Risks / Trade-offs

- A worker the coordinator never reconciled keeps its end unknown, so the peak is shown as at least N and may be higher than the real overlap → the label says so, and the figure matches what the wave selector counted; the suggestion never raises on an at-least peak
- `dispatch.json` is gitignored state and missing for older runs and for runs that never fanned out → the peak is unknown with a plain reason, the other numbers still report, and the suggestion holds
- The stretch counts time spent waiting for a person, quiet-hour waits, and untimed operator decisions in Decisions, so a long stretch can be idle time → the report and retro say so in words, every raise reason repeats it, and the suggestion is advice only. Splitting on those would mean reading free text or estimating
- A worker journal is missing or unreadable, or an auto fan-out is retro'd in a shell with a different level → an unreadable journal makes the stretch unknown and the suggestion hold; the run's limit comes from the ledger, and a limit that is unknown or differs from the configured one holds
- The ticket does not define an interrupt → the rule is settled and written down: every timed Stops line and every timed Approvals line. Scenarios pin it, including that an approval counts and that a date-only line does not
- Older date-only lines make a stretch unmeasurable → the conservative gap rule leaves out any gap such a line could have split, and a ledger with only older lines is unknown. The cost is that a ledger spanning the DS-6 change reports unknown or a shorter stretch than the real one, which can only make the suggestion hold
- Free-text stop lines cannot be assigned a stage → they are listed under unreadable lines and counted in the total, never dropped
- A stage word typed with different letter case would split a count → stages are lower-cased before counting
- The retro step is a markdown instruction run by a model → only its wording is pinned. The script's output is plain enough that a faithful paraphrase is easy to read back, and a failure is loud
- Refactoring `ledgerEntryProblems` to call `ledgerLineTime` could change the writer by accident → the writer's existing tests are unchanged and must stay green, and the new direct cases pin the same boundary lines
- The four-hour threshold is a judgement call → it is one named constant, stated in words in the retro step, so a later change is one line and one scenario

## Migration Plan

None. Nothing is stored and no setting changes. The script reads the next retro's ledger as it stands, older date-only ledgers give unknown or a conservative stretch, and removing the retro step and the script is a full rollback.

## Open Questions

None remaining. Operator accepted the recommended clarifications on 2026-11-16:

- Every timed Stops line and every timed Approvals line is an interrupt, including routine ones such as the `continuous-delivery: yes` approval at run start. That approval bounds the first stretch when it carries a UTC time.
- The conservative date-only gap rule stands: an older line with no time hides any gap it could have split. The ticket forbids estimating from date-only lines; the simpler reading that ignores untimed lines is rejected because it would overstate stretches on ledgers that straddle DS-6.
