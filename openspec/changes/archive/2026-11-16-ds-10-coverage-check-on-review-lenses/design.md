## Context

`/code-review-max` fans a change out to up to four lenses (`REVIEW_LENSES` in `factory/scripts/review-fanout.ts`), then writes each lens's candidate severities to `lens-candidates.json` and runs `review-fanout.ts adjudication`. A lens report today is its candidates or `NO FINDINGS`. It says nothing about which files the lens read. So a changed file that every lens skipped looks the same, in the output, as one that every lens read and found clean.

What the repository already gives this change:

- `measureReviewableDiff(numstat)` returns `paths`, the changed files with `NON_CODE_PREFIXES` (`openspec/`, `.delivery/`, `.review/`) already removed. `review-fanout.ts measure <base> <head>` prints it. The skill tells the reader to classify from `paths` only. This change leaves it as it is.
- A delta review already exists. `review-scope.ts` returns `scope: "delta"` with `since`, and the skill then says to use `since` wherever it would use the base. Because `since` is a commit of this branch's history, the three dot form resolves to `since` itself. `review-scope.ts` treats every file an earlier review covered as seen, and this change leaves that as it is.
- `planAdjudication` is a pure function with a thin command line, and `LensCandidates` carries severities only. The same shape fits a coverage planner.
- `lens-candidates.json` and every other per-review artifact live in `.review/mr-<iid>/<full-head-sha>/`.
- A review with no lenses already records the skip in `skipped-workers.json` and continues to adjudication with no candidates.

Findings from reading the repository, and what this change does about them:

- `measure` runs `git diff --numstat` without `-z`, so a renamed file appears as git prints it (`src/{old => new}.ts`) and a path with non-ASCII characters appears quoted. A brief built from that output would hand the lenses strings that are not real files. The coverage code therefore lists the changed files itself, with rename detection off and no quoting, and the brief takes its changed-path list from that same code. `measure` is not changed.
- `measure` keeps binary files and counts each as one changed line. A binary file has no text a lens can read, so the coverage code names binary files and does not send them to a focused pass.
- `review-scope.ts` records what an earlier review covered in `previousPaths`. A file that review left unexamined is in that set, so a delta review would never look at it again. The coverage code carries such files forward into the delta check.

## Goals / Non-Goals

- Goals: proof, per review, that every changed file was reported as examined by at least one lens or, failing that, by one focused pass; a plain list of any file still unexamined; rules that the script enforces, so no step depends on the conversation remembering or copying data correctly; no change to what adjudication verifies
- Non-Goals: measuring coverage inside a file; new lenses; a second focused pass; checking that a lens really read what it says it read; changing `measure`, `review-scope.ts`, the fan-out plan, or the verdict rules

## Decisions

- **Lens report contract.** Each lens ends its report with the line `Examined files:` followed by one `- <path>` line per file, or `Examined files: none`. It is present on `NO FINDINGS` too. A path is copied exactly as the brief's changed-path list writes it. Examined means the lens read the file's changed lines in the pinned diff or the file at the head. For a deleted file there is no head file, so it means the lens read the removed lines in the pinned diff. Naming a path from the brief or a diff header is not reading. A lens does not list a binary file. The main conversation reads the lens reports inline, so it transcribes each list into JSON for the script. The script is the strict part.
- **Where the logic lives.** `factory/scripts/review-fanout.ts` gains, next to `planAdjudication`, one function that turns git output into changed files, one pure planner, and their schemas. Nothing else holds a copy of the rules.
  - **Changed files, found by the script.** `git -c core.quotepath=false diff --numstat -z --no-renames <from>...<head>` is parsed by one function. `<from>` is the base in a full review and `since` in a delta review. The `-z` form gives raw paths with no quoting, and no rename detection turns a rename into the old path removed and the new path added, which are real paths. An entry whose counts are `-` and `-` is a binary file. Paths under `NON_CODE_PREFIXES` are dropped by the same constant `measure` uses. A path that holds a line break cannot be written in a report, so the command exits 1 and names it. Output order is the order git lists them. The result is `{ paths: string[], binary: string[] }` with `paths` holding the text files.
  - **Delta carry.** In a delta review, `--earlier <path>` names the earlier review's `lens-coverage.json`. The script reads it, requires its recorded head to equal `since`, and appends its `stillUnexamined` files, which are not already in `paths` and are not binary, to the checked files after the delta paths, marked `carried`. A file that appears in both is checked once. An earlier artifact with the status `skipped` carries nothing. A path to a file that does not exist records `earlier: "none"` and carries nothing, because reviews that ran before this check have no artifact. An earlier artifact that exists but cannot be read, or whose head is not `since`, exits 1. The carried files chain, because the earlier artifact's own `stillUnexamined` already holds what it carried.
  - `CoverageInput`: `{ scope: "full" | "delta", plannedLenses: (typeof REVIEW_LENSES)[number][], reports: { lens, examined: string[] }[], focused?: ({ path, status: "returned", examined: string[] } | { path, status: "failed" })[] }`. The input holds no path list. `plannedLenses` is the `lenses` array of the fan-out result. `focused` is absent until passes have run. It carries only outcomes new since the last run.
  - `CoverageResult`, which is also the artifact: `{ status: "checked" | "skipped", scope, from, head, earlier: "none" | "read", reason, checkedFiles, lenses, binary: string[], unexamined: { path, carried: boolean, focusedPass: "pending" | "examined" | "failed" }[], needsFocusedPass: string[], stillUnexamined: string[] }`. `from` is the base or `since`. `checkedFiles` counts the text files checked, carried ones included. `unexamined` is every checked file no lens listed, delta paths first and then carried ones, in listing order, whatever happened to it afterwards. `needsFocusedPass` is the `pending` ones. `stillUnexamined` is the `pending` and `failed` ones.
  - `planCoverage(input, changed, earlierArtifact, priorArtifact): CoverageResult`. Zod schemas with `.strict()` parse the input and both artifacts, and a failure throws.
- **Strict parsing, fail closed.** `planCoverage` throws, and the command exits 1 with a plain message and writes nothing, when: a planned lens has no report; a report names a lens that was not planned; two reports name the same lens; a report has no `examined` array; an entry is empty, absolute, starts with `./`, or holds a line break or NUL; an outcome names a path that is not unexamined; two outcomes name the same path; a `failed` outcome carries an examined list; a `returned` outcome has none or a malformed one; or an existing artifact for this review is unreadable or belongs to another head. A malformed report never becomes an empty list, because an empty list would turn every file into a focused pass.
- **One matching rule: exact, no trimming.** A path is compared as the exact string written. It is not trimmed, case-folded, or otherwise normalised, in the input check or in the match, and this is the only rule. An entry with whitespace around it is not malformed and matches nothing, so its file stays unexamined. A changed file is examined when some report holds the same string. Paths outside the checked files (files a lens opened to prove a claim, or files the script excluded) are ignored, never an error. A lens that mangles a path leaves that file unexamined and costs one extra focused pass. That is the safe direction: the failure adds cost, never false coverage. Normalising paths in the script was rejected, because it can equate two different files and the match then proves nothing. The brief's list comes from the same code that the check matches against, so the strings agree by construction and a mismatch can only come from a lens that rewrote one.
- **Binary and deleted files.** A binary file is listed in `binary`, counted by neither `checkedFiles` nor `unexamined`, never sent to a focused pass, and named in the Coverage section as a binary file that was not read as text. A lens listing one adds nothing. A deleted file is an ordinary changed file. A lens or pass examines it by reading its removed lines in the pinned diff, since the head has no copy. A carried file is examined by reading the file at the head, because an earlier review's change is not in the delta patch.
- **Skip rule.** `plannedLenses` empty with no `reports` returns `status: "skipped"`, `reason: "no lens ran, so there is nothing to check"`, `checkedFiles: 0`, and empty lists. The script does not call git in that case. `plannedLenses` non-empty with a missing report is an error, not a skip. `plannedLenses` empty with a report is an error too. The skip is written to `lens-coverage.json`. It adds no entry to `skipped-workers.json`, which already names `review-lens` for the same review, so the scorecard does not count one avoided worker twice.
- **The focused pass.** One fresh read-only subagent per `needsFocusedPass` file, on the `standard` model resolved earlier in the review. It gets the same brief and the pinned diff, one file path, and the instruction to apply the correctness and security checks and the tests and specification checks of lenses 1 and 2 to that file, reading outside it only to prove a claim. It returns candidates in the lens format and ends with its own `Examined files:` list. All passes run in one parallel batch. There is no cap on the count, because the requirement is one pass for each file, and the coverage step prints the number before it dispatches so the cost is visible.
- **The script decides a pass's outcome.** The conversation does not judge whether a pass examined its file. It records `returned` with the pass's list as transcribed, or `failed` for a pass that errored, timed out, returned nothing usable, or could not start. The script records `examined` only when a `returned` list holds the pass's own path, by the matching rule above. A `returned` list that omits the path is recorded `failed`. A pass that lists other files adds no coverage for them, because only the pass's own file counts.
- **No repeat, including on resume, enforced by reading the artifact.** The one-pass rule is carried by the artifact. Before it plans, the command reads `lens-coverage.json` at its output path when one exists. That artifact must name the same head, or the command exits 1. Every outcome the artifact recorded is kept, and the new outcomes in the input are added to them. An outcome for a file that already has a recorded one is refused with exit 1. A file with a recorded outcome is never in `needsFocusedPass`, even when a re-run lens report still leaves it unexamined. A resumed review that re-runs the lenses and writes a fresh input with no `focused` therefore dispatches nothing for files with a recorded outcome, and the rewritten artifact still holds those outcomes. A new outcome must name a file that is currently unexamined. A file that has a pass in flight when the review crashes has no recorded outcome and counts as not run, which is named in Out of Scope.
- **Merging candidates.** `LensCandidates` keeps its `severity`-only shape and `planAdjudication` is unchanged. The main conversation appends each focused pass's candidate severities to the `candidates` array of `lens-candidates.json` before running `adjudication`, and adds each pass's report file to the `--evidence` arguments of `review-packet.ts`, so the adjudicator sees the candidate text and not only its severity. Each pass's report is saved as `.review/mr-<iid>/<full-head-sha>/focused-pass-<n>.md`, `n` being the file's 1-based place in `unexamined`.
- **Failure behaviour.** A failed pass is recorded `failed`, the file stays in `stillUnexamined`, and the review goes on to adjudication. No retry, no stop. The Coverage section names the file. The verdict is not changed by coverage alone. The ticket asks only that the file be named and adjudication continue. Blocking on it is a separate decision for the operator and is left out.
- **Command line.** Two subcommands, both taking the commit the diff starts from and the head, so the script works the paths out and the conversation never copies them:
  - `review-fanout.ts paths <base-or-since> <head> [--earlier <lens-coverage.json>]` prints `{ paths, binary, carried }`, the checked files in order. The brief's changed-path list is this output.
  - `review-fanout.ts coverage <base-or-since> <head> <input.json> <lens-coverage.json> [--earlier <lens-coverage.json>]` reads and validates the input and any prior artifacts, finds the changed files, runs `planCoverage`, writes the result to the last path, and prints it. It writes nothing when validation fails. The script writes the artifact so that the one file the no-repeat rule depends on is not copied by hand.
  - Both follow the existing subcommands, which print JSON and exit 1 with a message on error, and extend their `USAGE` text. The invocation in `SKILL.md` is on one line and double-quoted, like the others.
- **Review flow in `skills/code-review-max/SKILL.md`.** The brief's changed-path list is the `paths` output, binary files marked, and in a delta review it is run with `since` and `--earlier`. A new `## Check coverage` section sits between `## Parallel review` and `## Adjudicate every candidate`.
  1. Write `lens-coverage-input.json` from the scope (`full` or `delta`), the fan-out result's `lenses`, and the lens reports. For no lenses, an empty plan and no reports. Add no path list.
  2. Run `bun "${FACTORY_ROOT}/scripts/review-fanout.ts" coverage "<base-or-since>" "<full-head-sha>" ".review/mr-<iid>/<full-head-sha>/lens-coverage-input.json" ".review/mr-<iid>/<full-head-sha>/lens-coverage.json"`, with `--earlier` in a delta review. Non-zero stops the review.
  3. For a `skipped` result, go to adjudication. Otherwise start one read-only subagent per `needsFocusedPass` file in one batch, on the standard model.
  4. Record each pass as `returned` with its list or as `failed` in `focused`, run the same command again, and merge the candidates as above. On a resumed review, run the command again from step 1 and dispatch only what `needsFocusedPass` returns.
  The existing sentence on an empty `lenses` array gains one clause: run the same coverage command, with no reports, so the skip is recorded. The lens report contract gains the `Examined files:` line. The output template gains a `### Coverage` section after Verification. In delta scope it counts and names the delta files and the carried files.
- **Output wording.** The Coverage section follows the human-facing output rule: plain sentences, no field names. It says how many changed files were checked and how many were reported as examined, names each file no lens examined and whether a focused pass then examined it or failed, names any file carried over from the earlier review, names binary files that were not read as text, and says when the check was skipped. It says the lists are the lenses' own reports. It does not use the word verified.
- **Docs.** `docs/reference.md`, `docs/workflow.md`, `README.md`, `factory/CONVENTIONS.md` and `openspec/specs/cost-efficient-routing/spec.md` each get the check described once, in the paragraph that already describes `review-fanout.ts`. Each states the self-reported limit. No file copies the artifact's field list, which stays in `review-fanout.ts`. `openspec/specs/` itself is changed at archive time from the delta spec in this change, not by hand.
- **Existing files touched:** `factory/scripts/review-fanout.ts`, `factory/scripts/review-fanout.test.ts`, `skills/code-review-max/SKILL.md`, `skills/delivery/checks/delivery-specs.test.ts`, `factory/scripts/workflow-contracts.test.ts`, `docs/reference.md`, `docs/workflow.md`, `README.md`, `factory/CONVENTIONS.md`. **No new source file.** `factory/scripts/record-skip.ts`, `review-scope.ts`, `review-packet.ts` and `measureReviewableDiff` are not changed.

## Risks / Trade-offs

- A lens's list is its own claim, so the check proves that each file was claimed, not that it was read. Accepted, because the ticket defines coverage as reported examination. The spec, `SKILL.md`, and the docs each say so, and the output says reported and never verified
- A lens that forgets or malforms its list stops the review. Accepted, because guessing would either flag every file or credit none. The message names the lens, and a fresh review run corrects it
- A lens that rewrites a path costs an extra focused pass for that file. Accepted as the safe direction. The brief and the check share one path list, so renames and non-ASCII paths no longer cause this by themselves
- A rename counts as two changed files, so a pure rename costs up to two passes. Accepted, because it is the only form whose paths can be matched exactly and the cost is bounded by the number of renames
- A large diff with sloppy lenses could start many focused passes. Accepted, because capping would leave files unexamined, which is the defect this change closes. The count is printed before dispatch and the passes use the standard model
- A focused pass that fails leaves the file unexamined and the review can still PASS. Accepted, since the ticket says adjudication continues. The file is named in the output, and a later delta review carries it forward until a pass examines it
- A carried file stays a candidate in every later delta review until it is examined. Accepted, because dropping it is the escape this change closes. A carried file that was reverted to the base costs one pass
- A path that holds a line break stops the review. Accepted as fail closed. The case is rare and the report format cannot carry it
- Binary files are named and never read. Accepted, because a pass on a binary file cannot examine it. The Coverage section keeps them visible
- Treating reading a file's changed hunks as examination makes a lens that was handed the whole diff easy to credit. Accepted, because the lens may state only what it read, and the focused pass exists for the files it did not
- A review resumed at the same head reuses the artifact. A stale artifact from a different head cannot be reused, because the file is inside the folder named by the full head SHA and the script also checks the head recorded in it

## Migration Plan

None. Reviews already in flight finish on the old report format. The next review that starts after merge uses the new one. Existing `.review` folders are not rewritten, and `lens-candidates.json` keeps its shape. A delta review whose earlier review has no coverage artifact carries nothing, and records that.
