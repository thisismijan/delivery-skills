## Context

The run ledger is a markdown file that every delivery stage reads and writes. Its Stops and Approvals sections hold lines that begin with a `yyyy-mm-dd` date, as the line templates in `skills/delivery/workflows/delivery-ledger.md` show. A date does not say how long a run went between operator interruptions, which a later retro needs.

Every ledger mutation already goes through one script, `factory/scripts/ledger-store.ts`, by the rule in `delivery-ledger.md` and the requirement "Concurrent writers cannot overwrite each other". That script today checks only the generation number, and it is the same script a worker journal write goes through. So it is the single place where a time form can be defined and enforced for every stage at once, without editing each stage's wording.

Finding from reading the repository: the ledger's Decisions section does not carry ISO timestamps today. Every ledger section, Decisions included, uses `yyyy-mm-dd`. The repository's ISO instants live elsewhere: lock owner records written by `ledger-store.ts` use `new Date().toISOString()` (with milliseconds), and many fixtures in `factory/scripts/*.test.ts` use the form `2026-10-22T10:00:00Z` (whole seconds and a literal `Z`). The form chosen below follows the second, because it is the one that reads well in a line of markdown.

## Goals / Non-Goals

- Goals: a UTC date and time on every new stop and approval line, from every stage; one definition and one check; older date-only ledgers accepted unchanged; a clear refusal when a new line has no time
- Non-Goals: backfilling older ledgers; times on any other section; a separate lint command; computing supervision metrics; rewording each stage workflow's own mention of Stops or Approvals

## Decisions

- **Time form:** `yyyy-mm-ddThh:mm:ssZ`, for example `2026-11-09T13:34:05Z`. Four digit year, 24 hour clock, whole seconds, a literal `Z`. No offset, no fraction, no space instead of `T`, and the time must be followed by a space or the end of the line, so `2026-11-09T13:34:05Zabc` is refused. One form keeps lines sortable and lets the later retro compute differences by plain string parsing. The form must also be a real calendar instant, so `2026-13-45T25:00:00Z` is refused.
- **Where the form lives:** `factory/scripts/ledger-store.ts` exports three things, and nothing else holds a copy.
  - `LEDGER_TIME_FORMAT`, the string `"yyyy-mm-ddThh:mm:ssZ"`, the placeholder the format page shows
  - `isLedgerTime(text: string): boolean`, true only when `text` matches the form by regular expression and `new Date(text)` is valid and `toISOString()` with the milliseconds dropped gives back the same text, which refuses impossible dates and `24:00:00`
  - `ledgerEntryProblems(previous: string, next: string): string[]`, the plain language messages for everything wrong with the Stops and Approvals sections of `next` compared with `previous`, empty when nothing is wrong. `writeLedger` joins them with newlines into the error message
- **Finding the sections:** a heading is a line whose text, trimmed of whitespace and carriage returns and lowercased, is `## stops` or `## approvals`. A section runs to the next line that begins `## `. Every occurrence is read, and the lines of all occurrences of one kind are one section, so a second `## Stops` heading further down is checked. A `### Stops` heading is not a match. Lines are split on `\r?\n`. This is not `land-gate.ts`'s reader, which reads the first heading only and is left as it is; exporting it would make the writer depend on the land gate.
- **What counts as a line:** every non-blank line in a section, trimmed of surrounding whitespace, not only bullets. So a bare `continuous-delivery: yes`, a `* ` bullet, and an indented continuation line are all lines and each must itself pass the check if new. A stop or approval entry is therefore one line, which the format page says.
- **Three problems, checked in this order, all reported:**
  1. *Lost section.* `previous` has a Stops or Approvals section and `next` has none of that kind. Message: `ledger lost its <Section> section; every section is kept.` This also catches a rename to `### Stops` and a dropped heading, either of which would hide new lines. Problem 2 is not reported again for a lost section.
  2. *Lost older line.* A line in a section of `previous`, counting repeats, has no matching line in the same kind of section in `next`. Message: `ledger <Section> section lost an older line: "<line>". Older lines are kept exactly as written; new lines start with a UTC time written as <LEDGER_TIME_FORMAT>, for example 2026-11-09T13:34:05Z.` An edited, dropped, or backfilled older line is refused here, for the right reason, and not as a new line that lacks a time. This enforces the append-only rule that `delivery-ledger.md` already states and the ticket's rule against backfilling.
  3. *New line without a time.* A line in `next` left over after matching `previous` as in problem 2 does not match `^- <time>( |$)` with the time accepted by `isLedgerTime`. Message: `ledger <Section> line has no UTC time: "<line>". Start new Stops and Approvals lines with a UTC time written as <LEDGER_TIME_FORMAT>, for example 2026-11-09T13:34:05Z.`
- **What a new line is:** the lines of `next` that remain after each line of `previous` has used up one equal line in `next`, counting repeats. For the first write of a ledger (`expected` of `-1`) `previous` is empty, so every line is new and no section can be lost. A date-only older line is left unchanged simply because it is carried over, and no rule guesses at the shape of a date-only line.
- **Where it is called:** `writeLedger` in `factory/scripts/ledger-store.ts`, after the existing generation checks in both branches, the first write (`expected` of `-1`) and the update, and before the temporary file is written. A stale write therefore still exits 4 with the stale generation message, and a refused first write creates no ledger file, because the file is only written after the check. This covers the run ledger and a worker journal, because both go through `writeLedger`. `nextLedger` is not changed.
- **Fail or warn: fail.** When `ledgerEntryProblems` returns anything, `writeLedger` throws a plain `Error`, which the command line turns into exit 1 with the message on standard error, as the existing generation-increment error is. The ledger is unchanged and the lock is released by the existing `finally`. A warning was rejected: the writer is run by agents, a warning on a successful write is easy to miss, and the date-only line would then be in an append-only ledger for good, so the measurement the ticket exists for would silently have holes. The cost of failing is one retry, and the message says exactly how to fix the line. This is the same fail closed stance the writer takes for a stale generation. No new exit code, stop id, or verdict is added.
- **Message wording:** the three messages above, one per problem, in plain language, each quoting the line as written. The form in them comes from `LEDGER_TIME_FORMAT`. No secrets are added, since the line is already the caller's input.
- **Ledger format page:** `skills/delivery/workflows/delivery-ledger.md` changes in three places. The Stops and Approvals line templates begin `- <yyyy-mm-ddThh:mm:ssZ>` in place of `- <yyyy-mm-dd>`. The write rule "Dates are UTC `yyyy-mm-dd`" says that Stops and Approvals lines begin with a UTC time in that form and every other section keeps `yyyy-mm-dd`. The page also says each Stops or Approvals entry is a single line, and that the writer refuses a new line without a time and an older line that is not kept exactly. The other stage workflows and skill files say "a Stops line" or "Approvals" and already tell the stage to read this page, so they are not edited and do not copy the form.
- **Older ledgers:** nothing is converted, backfilled, or rewritten. The append-only rule in `delivery-ledger.md` already says older entries are never edited, and the writer now enforces it for these two sections.
- **Existing files touched:** `factory/scripts/ledger-store.ts`, `skills/delivery/workflows/delivery-ledger.md`, `factory/scripts/ledger-store.test.ts`, and `skills/delivery/checks/delivery-specs.test.ts`. **New file:** `factory/scripts/fixtures/ledger-date-only.md` (new).
- **Fixture:** `ledger-date-only.md` is a short older ledger shaped like the format page, with no `Generation` header, one date-only line in Stops, and one date-only line in Approvals. Tests build every input by reading it and appending lines, so older lines are byte for byte the fixture's.

## Test seam

- Primary: `factory/scripts/ledger-store.test.ts` runs `ledger-store.ts` as a command against temporary state roots, the way the existing exit code test does, with inputs built from `factory/scripts/fixtures/ledger-date-only.md` (new). It asserts the exit code, the message text on standard error, the ledger file bytes after a refusal, the generation after a write, and the absence of a lock directory. It also calls `isLedgerTime` and `ledgerEntryProblems` directly for the malformed time shapes, the heading variants, and repeated identical older lines. The first write case uses expected generation `-1` and asserts the file does not exist afterwards. The stale case writes an input for generation 0 over a ledger at generation 1 and asserts exit 4. A worker journal case sets `DELIVERY_WORKER_JOURNAL` for the spawned process.
- Contract: `skills/delivery/checks/delivery-specs.test.ts`, in the existing "durable ledger writer" block, reads `LEDGER_TIME_FORMAT` out of `ledger-store.ts` source the way it reads the two invocation constants, then asserts the Stops and Approvals templates in `delivery-ledger.md` begin with it, that the write rule names both forms and the single line rule, and that no other Markdown file under `skills/`, found by walking the whole folder so every `SKILL.md` and workflow is covered, contains the text.
- What it catches: a new date-only or malformed line written by any stage, a refusal that changes the ledger, creates a file, or leaves a lock, an older ledger rejected, an older line edited, dropped, or backfilled, a heading variant, a second heading, or a dropped section that hides new lines, text joined to the time, a non-bullet line, a conflict masked by the new check, a format page that drifts from the script, and a copy of the form in another workflow
- What it misses: whether a stage, run by a model, remembers to write the time before calling the writer. The writer refuses the omission, so the failure is loud, and the model's judgement is not tested live
- Boundary that needs a fake: none. The writer is local and deterministic, so tests use real temporary files and no model, tracker, or forge
- Held-out samples: none are needed, because the rule is not written from sample data

## Risks / Trade-offs

- Failing a write can stop a stage at a terminal stop where it only needed to record that stop; accepted, because the message gives the exact fix and the retry is one write
- A stage that rewrites the whole ledger must reproduce every older Stops and Approvals line exactly, including its dashes and quotes; accepted, because the ledger is append-only and the refusal names the line that changed
- A single line per entry means a long operator quote cannot wrap onto a second line; accepted, since the line template is already one line
- A stage that writes its time from a local clock rather than UTC is not detected, only a missing or malformed `Z`; accepted, since the writer cannot know the author's clock
- Any ledger-like file written through the writer is checked, including worker journals, so a worker that wrote date-only stops starts failing; accepted, it is the same ledger rule and the journals are applied to the run ledger later

## Migration Plan

None. The check starts on the first write after merge and looks only at lines added by that write. Ledgers in flight keep their older lines as written and need only their next new stop or approval line to carry a time.
