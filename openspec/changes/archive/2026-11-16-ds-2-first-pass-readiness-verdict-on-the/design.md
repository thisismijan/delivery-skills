## Context

`/draft` already fail-closes on assessment, feasibility, the approach challenge (step 7a), and explain-back (step 7b). Explain-back asks whether a fresh reader can follow the change. It does not ask whether an implementer could build from it. A scenario with no observable outcome, a path that points at nothing, an interface the change never names, or a task list that disagrees with the specs all pass explain-back, because a reader can still restate them. This design adds a readiness check at the same point, using the same isolate-and-route pattern as explain-back, with a stricter model tier and a different stop.

## Goals / Non-Goals

- Goals: catch changes an implementer would have to guess at before verification; one revision then escalate; fail closed on a bad verdict; keep the reviewer on the change, never the ticket; make "marked new" and "which paths are checked" deterministic
- Non-Goals: judging the ticket; the explain-back check; skipping for any reason other than low complexity; retrying a malformed verdict with a fresh agent; changing the holdout review; changing the skip store beyond one worker name

## Decisions

- **Seam:** extend `factory/scripts/draft-route.ts` with a `readiness` mode and a `routeReadiness(verdict, attempt)` function, add a strict `ReadinessVerdict` and `parseReadinessVerdict` to `factory/scripts/verdicts.ts`, and add a read-only agent `factory/agents/first-pass-reviewer.md` (new). Routing, attempt bounds, and exit 3 stay in one script, as they do for the approach challenge and explain-back.
- **The one question:** the agent file asks only "could an implementer succeed on the first pass from this change alone?" and tells the reviewer to report nothing about style, naming, or whether the ticket was a good idea. The verdict schema backs that up: it has no item kind for style or naming, so such a finding cannot be expressed.
- **Verdict values:** `ready` and `not_ready`. A `ready` verdict has a non-empty `reasoning` and no items. A `not_ready` verdict has at least one item. Each item has a `kind` (`untestable_scenario`, `missing_file`, `unnamed_interface`, or `task_contradiction`), a `where` (the change file and the scenario or requirement inside it, or the path), and a `detail` that says what is wrong. Any other shape is refused.
- **The four definitions.** The agent file states these definitions and no others, so the check is the same on every run:
  - *Untestable scenario:* a scenario with no WHEN or no THEN, or whose THEN states no outcome a test could observe (for example "works correctly" or "is handled appropriately"), or that needs a live model or a person to judge.
  - *Referenced file neither present nor marked new:* a checked path (defined below) that cannot be read in the repository and is not marked new.
  - *Unnamed interface:* a function, type, command mode, exit code, configuration key, file format, or stop id that a requirement or decision needs, but that the change describes only in words ("a new helper", "a verdict") and never by the identifier an implementer would type.
  - *Task contradiction:* `tasks.md` has a task that proves a scenario the specs do not contain, or the specs have a scenario with no matching task, or a task names a path or interface that differs from the one the design names.
- **Which paths the missing-file rule checks.** A named path is checked only when all of these hold: it is written in backticks; it is repository-relative; it contains at least one slash; it ends in a recognised source extension (`.ts`, `.md`, `.json`, `.yml`, `.yaml`, `.py`, `.java`, `.sh`, `.toml`, or `.xml`); and it contains no angle bracket. The ending in an extension keeps words such as `and/or` and directory names out of the rule. These are never checked: a path that starts with `.review/`, `.delivery/`, `/`, or `<`; a path with an angle-bracket placeholder anywhere in it (such as `openspec/changes/<change>/proposal.md`); a runtime scratch file, meaning any path whose last segment is `skipped-workers.json`; and a bare filename with no directory (such as `tasks.md` or `generate-tasks.ts`). The draft step lists the checked paths in the dispatch prompt by this rule, and the agent file repeats the rule, so the list and the reviewer agree.
- **What "marked new" means.** A checked path is marked new when the proposal's Impact section or `design.md` writes the path in backticks and follows it, after one space, with the literal text `(new)`, for example `` `factory/agents/first-pass-reviewer.md` (new) ``. A mention in prose, a different spelling of the marker, or a marker on a different path does not count.
- **How the reviewer decides a path is present.** A checked path is present when a `Read` of that exact path, relative to the repository root named in the dispatch prompt, succeeds. The reviewer never uses `Glob` or `Grep` to decide presence, because they skip ignored folders such as the worktree folder a draft runs in, and would report every real file as missing. A path marked new is not read at all. This rule gives the same answer inside an ignored worktree as in a normal checkout.
- **Reading failures.** A `Read` that fails on a checked path that is not marked new is a `missing_file` item. The `detail` says either that the path is not present or that it could not be read, with the reason given by the failure. There is no separate item kind for a denied read. A path marked new is never a denied read, because it is never read.
- **Placement:** after explain-back (7b) proceeds and before `verify-change` (8). Explain-back's `proceed` action continues to this step instead of step 8. This step is numbered 7c in `skills/draft/SKILL.md`.
- **Tier:** frontier. The skill resolves the `frontier` tier to the exact available model, the same way the approach challenge does. The agent's tools are `Read, Grep, Glob` only.
- **Attempts:** `MAX_READINESS_CHECKS` is 2. On attempt 1, `not_ready` routes to `revise`. The revision fixes every reported item, regenerates `tasks.md` with `generate-tasks.ts`, and runs the check once more as attempt 2 with the same isolated inputs. On attempt 2, `not_ready` routes to `escalate`, which exits 3.
- **Stop id:** `unready-change`, added to the constitution draft stops and exported from `draft-route.ts` as a constant next to `UNSETTLED_COMPREHENSION_STOP`. It differs from `unsettled-comprehension`, because the two stops ask a person for different things: one says the change cannot be followed, the other says it cannot be built from.
- **Low complexity skip and its id:** when the feasibility `complexitySignal` is `low`, the step dispatches no reviewer and runs no route. It writes a skip file in the draft review folder naming the worker `first-pass-reviewer` with the skip id `first-pass-reviewer-<work-item-key>`, persists it with `record-skip.ts`, and refreshes `routing-scorecard.ts`, as step 7a does. The worker name is added to the closed `SKIPPED_WORKERS` list in `factory/scripts/record-skip.ts`. It cannot reuse `readiness-lens`, which already names a different worker. No other condition skips the check.
- **Re-draft and an already recorded skip:** `record-skip.ts` refuses a skip id that is already recorded, with the message `skip id already recorded: <skip id>` and exit 1, and a re-draft of the same work item reuses the same id. `record-skip.ts` needs no change for this beyond the worker name. The skill wording handles it: when persisting the skip exits 1 and the message is exactly that refusal for `first-pass-reviewer-<work-item-key>`, draft treats the skip as already recorded and continues to step 8. Any other persist failure stops the draft, and draft never invents a different skip id.
- **Fail closed on the verdict:** a missing or malformed verdict makes `draft-route.ts readiness` exit 1. The draft stops and escalates with one provider note naming the validator failure. It never retries the dispatch with a fresh agent and never treats the verdict as a pass.
- **Inputs to the reviewer:** only the change directory `openspec/changes/<change>/` (including `tasks.md`, which the contradiction check needs, and excluding the change metadata file that carries the work-item key) and the checked paths, which the dispatch prompt lists. Never the work item, grooming decisions, grilling history, or anything under `.review/draft-`.
- **Existing files touched:** `skills/draft/SKILL.md`, `factory/scripts/draft-route.ts`, `factory/scripts/verdicts.ts`, `factory/scripts/record-skip.ts` (worker name only), `skills/delivery/sdlc-constitution.json`, `factory/CONVENTIONS.md` (the read-only subagent list and the model policy line), `docs/reference.md` (a readiness section beside the approach challenge), `factory/scripts/workflow-contracts.test.ts`, and `factory/scripts/explain-back.test.ts`.
- **New files:** `factory/agents/first-pass-reviewer.md` (new) and `factory/scripts/first-pass-readiness.test.ts` (new). Both are marked new here so the reviewer's own rule holds for this change.
- **Step-order assertions to update:** the assertions in `factory/scripts/explain-back.test.ts` that explain-back is the last gate before verification, and the draft step-order checks in `factory/scripts/workflow-contracts.test.ts`, now state that explain-back precedes readiness and readiness precedes verification.
- **Stacking:** this change assumes the explain-back change is in place (`factory/scripts/draft-route.ts` `routeComprehension`, `ExplainBackVerdict` in `factory/scripts/verdicts.ts`, `factory/agents/explain-back-reader.md`, and the `unsettled-comprehension` stop). Its ordering requirement lives in this change's own capability, because the explain-back capability is not yet in the main specs to modify.

## Test seam

- Primary: unit tests in `factory/scripts/first-pass-readiness.test.ts` (new) of `parseReadinessVerdict` (accepted and refused shapes, including a `missing_file` item whose detail says the path could not be read) and of `routeReadiness` (a hand-written not-ready verdict of each of the four kinds routes to `revise` on attempt 1; `escalate` with the `unready-change` stop and exit 3 on attempt 2; `proceed` on ready; a refused attempt outside 1 to 2)
- Contract: `factory/scripts/workflow-contracts.test.ts` asserts the draft skill names the step, sits it after explain-back and before verification, states that a not-ready verdict does not continue to step 8, states the isolation rule, the checked-path rule, the no-fresh-agent-retry rule, the skip id, and the already-recorded handling, and shows the route invocation. It also asserts that the agent file is read-only on the frontier model, asks the one question, states the four definitions, the checked-path rule, the marked-new rule, and the Read-not-Glob presence rule, and that `SKIPPED_WORKERS` contains both `first-pass-reviewer` and `readiness-lens`
- Constitution: a stop test asserts the draft stops include `unready-change` and `unsettled-comprehension` as two distinct ids
- What it catches: wrong routing, a malformed or contradictory verdict accepted, a missing or mis-ordered step, a leaked work item in the dispatch description, a colliding worker name, a missing stop, a skill or agent file that drops a rule
- What it misses: whether the live model applies the definitions well, such as telling a real untestable scenario from a testable one, or recognising a path under the checked-path rule. That is a model judgement and is not tested live. The wording of each rule is pinned, and the live application is left to later drafts
- Boundary that needs a fake: the model reviewer itself. Tests feed `parseReadinessVerdict` and `routeReadiness` hand-written verdicts and never dispatch the agent
- Held-out samples: none are needed, because the rule is not written from sample data

## Risks / Trade-offs

- Frontier tier cost on every medium or high complexity draft; accepted because a change that is not ready costs a failed build, and the low complexity skip removes the check where it is least likely to pay
- A strict reviewer may report items an implementer would have resolved on their own; mitigated by closed definitions, one revision, and a person at the end
- Inserting a step after 7b breaks step-order assertions in two test files; those updates are listed above so they are not forgotten
- The `(new)` marker is a convention the author must follow; the reviewer reports a missing marker as a missing file, and the one revision fixes it
- A path that does not match the checked-path rule (a directory, or a bare filename) is never verified; accepted, because a wrong guess there is cheaper than a false stop on every placeholder

## Migration Plan

None. Behaviour starts on the next `/draft` after merge. Drafts already in flight are unaffected until they reach this step.
